# T3.3 Detector equivalence test (`ardoco-id` against the standalone ArDoCo runner)

Milestone M3 · Effort M · Depends on: T3.1 · Checks RK-3 and RK-22

Status: done (2026-10-17), open points listed at the end

## Context

T3.1 added the detector `ardoco-id`. `BenchmarkEquivalenceTest` of `detector-ardoco` already compares the detector hooks with the standalone ArDoCo runner on MediaStore. That test feeds the links with its own TLR run inside the ID branch. It does not use the links of the `ardoco` TLR approach and it does not use the KG.

T3.3 adds the end-to-end check. The TLR links of the approach `ardoco` (T2.1) are the input of the detector. The test compares the findings with the standalone runner on benchmark projects. T3.3 also owns two checks of the plan: ArDoCo on the Quarkus classpath (RK-22) and the alignment rate per project.

## Goal

With `linkApproaches: [ardoco]`, the detector finds the same model elements as the standalone runner on at least 2 benchmark projects. The text findings are the same, except for documented deviations.

## Scope

1. Record the TLR links of the approach `ardoco` as CSV files (`modelElementID,sentence`, 1-based sentence).
2. Add a KG-free test in `detector-ardoco` (7 cases). It feeds the links to `IdRunner.run` through the one-sentence-per-line rendering.
3. Add a KG test in `inconsistency-agent` (4 cases). It seeds the KG with TextUnits, ModelElements and TraceLinks with approach `ardoco`. It runs `DetectionService` with `linkApproaches: [ardoco]`.
4. Report the alignment rate per project.
5. Run ArDoCo on the Quarkus classpath of `inconsistency-agent`.

## Decisions

| # | Question | Decision [default] |

| 1 | Where do the TLR links come from? | [Recorded CSV files in `detector-ardoco/src/test/resources/tlr-ardoco-links`.] A test dependency on `approach-ardoco` brings the release `pipeline-tlr` onto the same classpath as the branch `pipeline-id`. The classes clash. The files come from `BenchmarkEquivalenceTest` of `approach-ardoco`. |
| 2 | Which projects? | [MediaStore (PCM, UML), TeaStore (PCM, UML), TEAMMATES (PCM), BigBlueButton (PCM), JabRef (PCM) in the KG-free test. MediaStore and TeaStore in the KG test.] The KG-free test has 7 cases. The KG test has 4 cases. |
| 3 | What is the baseline? | [`StandaloneBaseline`: annotate the raw golden text, then run `IdRunner.standalone`.] The test-jar of `detector-ardoco` shares the helper with the KG test. |
| 4 | How are the TLR links and the standalone links different? | [Tolerate extra text findings only when a documented `extra` entry lists them.] MediaStore has 18 links from the release TLR and 29 links from the TLR of the ID branch. The detector then reports two more words: `download` in sentence 9 and in sentence 37. All other cases are equal. |
| 5 | How to check the Quarkus classpath? | [Run the KG test in `inconsistency-agent`.] This module has the Quarkus BOM. The test starts CoreNLP and ArDoCo there. |
| 6 | Double-run experiment of T3.1 decision 7? | [Not done.] The task needs no second run. See open points. |

## Acceptance criteria

1. For all 7 KG-free cases, `stats.unmapped` is 0.
2. The model-element ids equal the standalone ids in all cases.
3. The text findings equal the standalone findings. The only exception: the `extra` entry of the MediaStore cases.
4. The same holds for the 4 KG cases on the findings in the KG (`undocumented-model-element`: involved keys, `missing-model-element`: sentence and word).
5. The alignment rate is 100 % for each project.
6. ArDoCo runs on the Quarkus BOM classpath without errors from protobuf or JNA.
