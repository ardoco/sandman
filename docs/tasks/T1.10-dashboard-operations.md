# T1.10 Dashboard operations (workflows, events, alerts, record/replay)

Milestone M1 · Effort M · Depends on: T1.9 · Blocks: M1 exit

Status: done (2026-10-09). Alerts, operations, event viewer, resources and history exist with tests.

## Context

T1.9 delivers the `dashboard` service with admin login, the status poller cache, the services, graph and gateway pages. This task adds the operator pages that act on or watch the running system. The dashboard's only write paths into SANDMAN are workflow cancel and dead-event replay through the orchestrator API, authenticated with `svc_token_dashboard`; the orchestrator records them as `service:dashboard` (it rejects `X-Sandman-Actor` from callers other than the query-service). ## Goal

Pages **Workflows**, **Events** and **Experiments**, plus an alert banner on every page and one structured log line per alert transition, in `services/dashboard`.

## Scope

1. **Workflows page** (orchestrator client with the dashboard token, base URL from the `orchestrator` entry of `SANDMAN_TARGETS`, 5 s timeout): list with filters `projectId`, `status` and `nextCursor` paging; detail with steps (agent, skill, status, attempts, A2A task id, start/end, duration, `error.code`/`message`/`retryable`; `input`/`result` as collapsed, escaped JSON); htmx refresh every 5 s while the workflow is `PENDING`/`RUNNING`. Cancel button for `PENDING`/`RUNNING`/`BLOCKED` workflows: POST form with CSRF and `hx-confirm`, forwards to `POST /v1/workflows/{id}/cancel`; 404 and 409 problems shown as messages.
2. **Dead events:** list (`eventId`, `type`, `error`, `receivedAt`) and replay button (CSRF, `hx-confirm`) → `POST /v1/dead-events/{eventId}/replay`; 404 shown as message.
3. Orchestrator unreachable or 5xx: the pages render with a "orchestrator unreachable" message, never a 500 and never the upstream body. Each cancel/replay writes an audit log line (`event=admin_action`, `action`, `target`, upstream status).
4. **Events page:** one NATS ephemeral **ordered** consumer on `sandman.>` (no acks, no durable), started at `max(1, lastSeq − 499)` and kept in an in-memory ring buffer of 500 events; resubscribes after reconnects. Filters by type and project (envelope `subject`); list newest first with `id`, `type`, `subject`, `time`, `source`, `correlationid`; payload view as escaped, pretty-printed JSON truncated at 64 KiB. Consumer pending/ack-pending/redelivered counts and stream size from the T1.9 `/jsz` cache.
5. **Experiments page:** `llm-replay` status from the poller cache: mode, experiment, cassette entries, hits, misses, recorded, forwarded, last activity; misses in `replay` mode highlighted; "llm-replay down" when the target is down.
6. **Alerts.** Evaluated after each poll from cached data; in-memory state per alert key; one log line `event=alert` with `alert`, `key`, `state=raised|cleared` and a short message per transition (no repeats while the state holds). Rules (Stage 1 §10.1): service or infrastructure component `down` for more than 30 s; a workflow `FAILED` or `BLOCKED` (from `GET /v1/workflows?status=…`, one key per workflow id, updated within the last 24 h); dead events exist; a gateway budget ≥ 80 %; Memgraph memory ≥ 80 % of its limit (`SHOW STORAGE INFO`, field names to verify). Banner in `base.html` (htmx refresh every 5 s) lists active alerts with links to the relevant page.
7. Navigation entries in `base.html`; no new secrets, env vars or Compose changes expected.

Out: manual workflow triggers (console), event publishing or replaying arbitrary events, alert notification channels other than the log (ADR-0011: log-based), persistent alert history (T1.11 history covers health only).

## Acceptance criteria

- **Orchestrator client:** against a fake orchestrator (ASGI app), list/detail/paging render; cancel and replay send the dashboard bearer token, no `X-Sandman-Actor`, and require a valid CSRF token (403 otherwise) and a session (401/redirect otherwise); 404 and 409 are shown as messages; orchestrator down → page renders with the message.
- **Integration with the real orchestrator app** (`create_app` from `sandman_orchestrator.app` with a test token verifier containing `dashboard`): cancel of a running workflow → 202 and steps `CANCELED`; replay of a dead event → 202.
- **Event viewer is read-only:** with a real NATS (Testcontainers `nats:2.15.0-alpine -js`), events published via `sandman_agent.events` appear in the viewer; after the viewer ran, the durable `orchestrator` consumer's delivered and ack floor sequences are unchanged and no new durable consumer exists.
- **Alerts:** table-driven tests per rule: raised exactly once, cleared exactly once, `down` for 29 s raises nothing, 31 s raises; log lines are JSON with `event=alert`; banner shows active alerts.
- **Escaping and secrets:** an event payload and a step error containing `<script>` render escaped; no token or password appears in pages or logs (extend the T1.9 secret-leak test to the new pages).
- **E2E** (extend `tests/e2e/test_dashboard.py`): after the walking skeleton, the Workflows page lists its workflows with status `SUCCEEDED`, the Events page shows its `sandman.ingestion.completed` event, the Experiments page shows mode `live`.
- `uv run ruff check`, `ruff format --check`, `uv run pytest services/dashboard` green.

## Open questions (decided 2026-10-08: recommended defaults accepted)

1. The orchestrator accepts the dashboard token for **all** admin operations including `POST /v1/workflows` (`ADMIN_CALLERS` in `app.py`), while Stage 2 §1.5 and ADR-0016 allow only cancel and replay: **restrict the dashboard to cancel and replay in the orchestrator as part of this task (small change plus test)**, or accept and document it.
2. Admin identity in the orchestrator's records: **`service:dashboard` plus the dashboard's own audit log line** (no change), or allow the dashboard as a second trusted forwarder of `X-Sandman-Actor` (library and contract change).
3. Alert state after a dashboard restart: **in memory only; active conditions are raised again after restart**, or persist in the dashboard SQLite.
4. Dismissing alerts: **no dismiss; an alert clears when its condition ends (workflow alerts after 24 h or when the workflow leaves `FAILED`/`BLOCKED`)**, or a per-alert acknowledge button.
