## Context

The `ardoco` approach (T2.1) annotates the KG rendering in process with CoreNLP 4.5.10 (`ArdocoApproach.nlp()`, `ssplit.eolonly=true`) and injects the result as `PreprocessingData`. The models jar (464 MB) makes the tlr-agent image 1.84 GB. The user wants CoreNLP only from the Stanford CoreNLP provider service (`ardoco/stanfordcorenlp-provider-service`): the KIT instance `https://vdl-ws.sdq.kastel.kit.edu/stanfordnlp`, or a local compose service if the KIT instance is not reachable. The KIT instance needs credentials that the user fills in. Read first:
- `docs/tasks/T2.1-ardoco-tlr-adapter.md` (implementation notes), `docs/notes/spike-T0.12.md` §4 (presplit), §6 (dependencies)
- `deploy/docker-compose.yml` (networks `internal`/`egress`/`llm-local`, `llm-gateway`, `edge-proxy`), `deploy/gen-secrets.sh` (file secrets, `MOUNTED` modes), `deploy/check-env.sh`, `deploy/proxy/Caddyfile`, `Makefile` (`e2e`, `up`)
- Code: `services/tlr-agent/approach-ardoco/src/main/java/.../tlr/ardoco/ArdocoApproach.java`, `.../BenchmarkEquivalenceTest.java`, `services/tlr-agent/src/main/java/.../tlr/RecoverTraceLinks.java` (approach failure isolation), root `pom.xml` (`corenlp.version`, models jar pin)

Findings (checked 2026-10-10; ArDoCo `v2.1.0`, service commit `825b98e`):
- **Service API.** `POST /stanfordnlp` with JSON `{"text": "<URL-encoded text>"}` returns the ArDoCo `text-provider-json` DTO (sentences, words with POS, lemma, dependencies, constituency tree). `GET /stanfordnlp/health` returns `Microservice is healthy` without authentication. All other paths need HTTP Basic. The server reads `USERNAME`/`PASSWORD` from the environment and stores the user in an H2 file database. `/h2` (H2 console), `/swagger-ui`, `/v3/api-docs` and `POST /stanfordnlp/registration` (ADMIN) also exist.
- **No per-request properties.** The annotators are fixed (`tokenize,ssplit,pos,parse,depparse,lemma`, same as ArDoCo's `TextProcessorLocal`). The service has no `ssplit.eolonly` and no other split option. It builds a new `StanfordCoreNLP` pipeline for every request (model load per call). The CoreNLP version comes in through ArDoCo `text-preprocessing` (4.5.10 at ArDoCo 2.1.0). No endpoint reports a version.
- **ArDoCo client.** `text-preprocessing` (`ConfigManager`, `TextProcessor`, `TextProcessorService`, `HttpCommunicator`, `MicroserviceChecker`) switches to the service with `NLP_PROVIDER_SOURCE=microservice` and `MICROSERVICE_URL` (paths `corenlpService=/stanfordnlp`, `healthService=/stanfordnlp/health` from `config.properties`). Credentials: `SCNLP_SERVICE_USER`, `SCNLP_SERVICE_PASSWORD` (HTTP Basic, Apache HttpClient 5). It retries an `IOException` twice, then **falls back silently to local CoreNLP**; conversion errors fall back at once. The settings are JVM-wide (`ConfigManager.INSTANCE`, read once from the environment or a `.env` file).
- **KIT instance.** `GET /stanfordnlp/` and `GET /stanfordnlp?text=Hi.` answer 401 (`WWW-Authenticate: Basic realm="Realm"`). `GET /stanfordnlp/health` answers 200. The instance is reachable and runs this service. Its version is unknown.
- **Images.** `ghcr.io/ardoco/stanfordcorenlp-provider-service`, tags `0.1.0` to `1.0.0` (2024-03-07) and `latest`. `latest` is rebuilt on every push to `main` (Spring Boot 4.2.0-M2, Java 25). The `Dockerfile` sets `USERNAME=admin`, `PASSWORD=changeme` and no heap limit. Licence MIT.
- **CoreNLP elsewhere in ArDoCo.** `code-traceability` (`arcotl/NameComparisonUtils`, used by TransArC SAM↔code) runs its own in-process pipeline `tokenize,pos,lemma`. It needs the models jar. SWATTR (T2.1) and ArDoCode (SAD↔code) do not use it.

## Goal

No ArDoCo path in SANDMAN annotates text with in-process CoreNLP. The tlr-agent (and later the inconsistency-agent) reaches CoreNLP only through the internal service `corenlp-gateway`. The gateway forwards to the KIT instance (`remote`) or to a local provider container (`local`). Sentence *i* stays line *i*. The equivalence test of T2.1 still holds with the same provider on both sides.

Upstream (repository `ardoco/stanfordcorenlp-provider-service`, one PR, then a release tag and image):

In this repository:
1. **Service `corenlp-gateway`** (new compose service and site component). Image: the pinned `caddy` image of `edge-proxy`; config `deploy/corenlp-gateway/Caddyfile`. Networks: `internal`, `egress`, `corenlp-local`. It listens on `:8080` and forwards only `POST /stanfordnlp`, `GET /stanfordnlp/health` and `GET /stanfordnlp/version`; every other path answers 404 (no `/h2`, `/swagger-ui`, `/registration`). It replaces any incoming `Authorization` header with the credentials of the active mode (`header_up`). Timeouts: dial 10 s, response header 300 s. A small entrypoint reads the credentials file, base64-encodes `user:password` and starts Caddy, so no secret is in the compose file or the image. Healthcheck: `GET /stanfordnlp/health` through the gateway.
2. **Modes** (one config switch `SANDMAN_CORENLP_MODE`, default `remote`):
   - `remote`: upstream `SANDMAN_CORENLP_URL` (default `https://vdl-ws.sdq.kastel.kit.edu`; the path `/stanfordnlp` is kept). Credentials: file secret `corenlp_credentials` (one line `user:password`), mounted **only** into `corenlp-gateway`.
   - `local`: upstream `http://corenlp-provider:8080`. Credentials: file secret `corenlp_local_credentials` (generated), mounted into `corenlp-gateway` and `corenlp-provider`.
   - No `auto` mode (open question 2).
3. **Service `corenlp-provider`** (profile `corenlp-local`). Image `ghcr.io/ardoco/stanfordcorenlp-provider-service:<release with U-1>@sha256:<digest>` (interim: `1.0.0@sha256:<digest>`). Network `corenlp-local` only (internal: gateway ↔ provider, like `llm-local`). The entrypoint reads `corenlp_local_credentials` into `USERNAME`/`PASSWORD` and starts the jar; `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75`; `mem_limit` from the measurement in the acceptance criteria [4g]. The H2 file stays in the container (no volume; the user is re-created at start). Mode `local` adds `--profile corenlp-local` in the `Makefile` targets (`COMPOSE_PROFILES`). `corenlp-gateway` gets `depends_on: corenlp-provider: {condition: service_healthy, required: false}`. Agents do not wait for the gateway's health, so a KIT outage does not block the stack start.
4. **Adapter** (`approach-ardoco`, version `2.1.0+a2`):
   - Remove `nlp()` and all `edu.stanford.nlp` use. Add a small HTTP client (`java.net.http`) for `SANDMAN_CORENLP_URL` (tlr-agent default `http://corenlp-gateway:8080`). It POSTs `{"text": URLEncoder.encode(text), "eolonly": true}` and converts the answer with ArDoCo's `JsonConverter.fromJsonString` and `DtoToObjectConverter.convertText` (`text-provider-json`, the same path as `TextProcessorService`). The result is injected as `PreprocessingData`, as in T2.1. ArDoCo's own provider selection (`ConfigManager`) is never used, so its silent local fallback cannot run.
   - **1:1 check.** The answer must have exactly one sentence per rendered line, and sentence *i* text normalized must equal line *i*. A mismatch fails the run (not retryable) and names the first differing line.
   - **Interim split** (service without U-1, detected by `/stanfordnlp/version` returning 404): render the lines separated by one blank line (`"\n\n"`). CoreNLP's default `ssplit.newlineIsSentenceBreak=two` then always breaks between lines. A split inside one line still fails the 1:1 check. Remove the interim path when the KIT instance runs U-1.
   - Annotate each document version once per `recover` call and reuse the `Text` for all its models (removes the `ponytail` note of T2.1).
   - **Failures.** Retry connect errors, 429, 502, 503 and 504 up to 3 attempts with 2 s and 8 s backoff. Then the run fails as **retryable** (below). 401 and 403 fail at once, not retryable, with the message "CoreNLP credentials rejected: check deploy/secrets/corenlp_credentials". A request takes at most `SANDMAN_CORENLP_TIMEOUT` [300 s].
   - **Retryable approach failure** (SPI, internal): `ApproachUnavailableException`. `RecoverTraceLinks` finishes the other approaches, records the `ardoco` Run as failed, and then fails the skill with `DEPENDENCY_UNAVAILABLE`, `retryable: true`, so the orchestrator retries the step (T0.8). Other runtime errors keep the T2.1 isolation (Run failed, skill completes).
   - **Provider identity.** Log the `/stanfordnlp/version` answer (or `unknown`) on every run. It enters `configHash` (open question 5).
5. **Image size.** In `approach-ardoco`, exclude `edu.stanford.nlp:stanford-corenlp` from `pipeline-tlr` and declare the code jar (no `models` classifier) again. Record the image size before and after in the implementation notes (expected about 1.84 GB → 1.38 GB).
6. **Secrets and checks.** `gen-secrets.sh` writes `corenlp_credentials` with the placeholder `change-me:change-me` (never overwritten) and `corenlp_local_credentials` as `sandman:<rand>`. ## Network design (decided by the user)

The agents stay on `internal` (no egress) and hold no CoreNLP credentials. Only `corenlp-gateway` is on `egress`, as `llm-gateway` is.
- **Egress scope.** Docker networks cannot filter by destination host. The gateway is a reverse proxy with one upstream fixed at start and a path allowlist. It is not a forward proxy, so callers cannot choose a host. This is the same trust model as `llm-gateway`. A host firewall rule is out of scope (open question 6).
- **Why Caddy.** The pinned image is already in use (`edge-proxy`). Reverse proxy, path matcher, header rewrite, TLS to the upstream and timeouts are configuration only. No code is needed.
- **Why a profile for `local`, not Docker-socket access.** A compose profile with a sibling service needs no privileges. A gateway that starts containers needs the Docker socket, which is root-equivalent (the `resources` profile carries this warning already). `COMPOSE_PROFILES` and `depends_on … required: false` cover the start order.

## Acceptance criteria

- No class in `approach-ardoco` or `tlr-agent` imports `edu.stanford.nlp.pipeline` (ArchUnit). The runtime classpath has no `edu/stanford/nlp/models/`. The image is smaller by the models jar; the sizes are in the implementation notes.
- `BenchmarkEquivalenceTest` against the local provider container: MediaStore, TeaStore, TEAMMATES, BigBlueButton and JabRef, each with PCM and UML, give equal link sets for adapter and standalone. Any project excluded by the 1:1 check is reported with counts; MediaStore and TeaStore must not be excluded (M2 exit).
- Two runs on the same input give the same link ids and `configHash`.
- `remote` mode on the user's machine with real credentials: the MediaStore links equal the `local` links, or the difference is reported with both provider versions.
- Wrong credentials: the `ardoco` Run fails at once with the credentials message, not retryable. Gateway stopped or upstream down: the Run fails after the retries, and the skill fails with `DEPENDENCY_UNAVAILABLE`, `retryable: true`; the other approaches' links are written.
- From inside `tlr-agent`, a request to `https://vdl-ws.sdq.kastel.kit.edu/stanfordnlp/health` fails (no route). The gateway answers 404 for `/h2` and `/stanfordnlp/registration`. `docker inspect tlr-agent` shows no CoreNLP secret.
- `check-env.sh` fails for mode `remote` with the placeholder, an empty part or a missing file, and passes for mode `local` without the remote file (shell test).
- `corenlp-provider` measured on TEAMMATES (largest text): peak RSS, first-request and later-request latency, image size. `mem_limit` is set from it with ≥ 25 % headroom.
- `make e2e` and CI stay green in mode `local`; e2e < 15 min. `replay-twice` stays identical.

## Implementation notes (2026-10-11)

- **Gateway access (security review).** `corenlp-gateway` is not on `internal`. The dedicated internal network `corenlp` holds the gateway and `tlr-agent` (the inconsistency-agent joins with T3.1). Callers authenticate with HTTP Basic (`user` = agent name, password = secret `corenlp_client_token_<agent>`), checked by Caddy `basic_auth` (bcrypt, constant-time; the entrypoint hashes the tokens at start). A bearer token would be compared as plain string by Caddy's header matcher. A request without a valid token gets 401 and never reaches the upstream. The container healthcheck uses a loopback-only listener (`127.0.0.1:8081`) that serves the health path only.
- **Adapter.** `CorenlpClient` (`java.net.http`). The answer is read with ArDoCo's `JsonHandling.createObjectMapper()` and converted with `DtoToObjectConverter`. `JsonConverter.fromJsonString` is not used: it validates against a schema with json-schema-validator 2.0.0, and the contracts pin 3.0.8 (`NoSuchMethodError`). The 1:1 check guards the shape. The provider identity (`/version` answer or `unknown`, plus the eolonly mode) enters `configHash` through `TraceLinkApproach.environment(ctx)`. Version `2.1.0+a2`.
- **Parity (manual, `-Dcorenlp.parity=true`).** Service `1.0.0` DTO equals in-process CoreNLP 4.5.10 DTO for MediaStore (37 sentences), TeaStore (43), TEAMMATES (198), BigBlueButton (87), JabRef (13). Not run against the KIT instance (no credentials).
- **Equivalence.** `BenchmarkEquivalenceTest` against the provider container on both sides: all ten cases equal, no project excluded (sentence counts equal line counts). Provider peak memory 1587 MiB (cgroup peak, includes page cache) after all ten cases.
- **Image size.** tlr-agent image `1.62 GB` before (models jar 474 MB inside), `667 MB` after (`docker images`).
- **Provider image.** `1.0.0` is `linux/amd64` only. On Apple silicon it runs emulated.
