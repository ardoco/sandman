# T9.1 – Automatic artifact classification and re-classification

Status: done · Owner: extraction-agent · Date: 2026-11-08

## Problem

1. The kind of a file (`requirements`, `architecture-doc`, `architecture-model`, `code`, `test`, `other`) comes only from client-side `kindRules`. An archive uploaded without rules (partial upload without manifest, API clients, scripts) turns every file into `other`. No trace link recovery runs for such a project.
2. The kind is set once, at artifact creation (`ON CREATE SET a.kind`). A later rule change does not re-classify existing artifacts. The pitfall is documented in `docs/user/ingesting-artifacts.md`.

## Solution

1. **Heuristic fallback.** Explicit `kindRules` keep precedence. If no rule matches, `classify.guess(path, head)` decides from path segments, file suffix and the first 4 KiB of content. It returns `(kind, format | None)`. It never guesses `other` by accident: if no signal exists, the kind is `other`.
2. **Re-classification.** If the kind of an existing artifact differs from the new classification, the ingestion updates `Artifact.kind` and re-activates the current version. The normal event chain (extraction, trace link recovery) then runs. A fallback result of `other` never overrides an existing non-`other` kind. An explicit rule always applies.

## Heuristic (first match wins)

| Signal | Kind | Format |
|---|---|---|
| suffix `.repository`, `.uml`, `.xmi` | `architecture-model` | by suffix |
| path segment `test`, `tests`, `__tests__`, `spec`, or file name `*Test.*`, `*Tests.*`, `test_*`, `*_test.*`, `*.test.*`, `*.spec.*` with a code suffix | `test` | – |
| code suffix (`.java .kt .scala .py .js .jsx .ts .tsx .go .rs .c .h .cpp .hpp .cc .cs .rb .php .swift`) | `code` | – |
| suffix `.csv` and header with columns `id` and `text` | `requirements` | `csv` |
| suffix `.md`, `.markdown`, `.txt`, `.pdf`, `.docx`, `.rst`, `.adoc` and path segment or file stem matches `requirement(s)`, `req`, `reqs`, `srs`, `user-stories`, `stories`, `features` | `requirements` | – |
| `.md` with at least two headings whose first word matches an id (`REQ-1`, `FR-12`) | `requirements` | – |
| same document suffixes and path segment or stem matches `architecture`, `arch`, `design`, `sad`, `adr`, `decisions`, `c4` | `architecture-doc` | `adr` if segment is `adr`/`decisions` and suffix is `.md` |
| other document suffixes under `docs`, `doc`, `documentation`, `wiki` | `architecture-doc` | – |
| anything else | `other` | – |

Files that are `requirements` and `.md` need the requirement parser. A `.pdf` or `.docx` classified as `requirements` stays a plain document (existing behaviour of the kind).

## Steps

1. `services/extraction-agent/src/sandman_extraction/classify.py` with `guess`, plus unit tests.
2. Wire into `Manifest.kind_of` callers in `ingest.ingest` (content from the archive, or from the store for unchanged hashes), including re-classification.
3. Tests: ingestion without rules classifies; rule overrides heuristic; rule change re-classifies and re-activates; `other` fallback never downgrades.
4. Docs: `docs/user/ingesting-artifacts.md` (heuristic table, remove the pitfall), README status line.
5. Verify: `uv run pytest services/extraction-agent`, `make lint`, `make contracts`.

## Not in scope

A review UI for classification, an LLM classifier, and per-project classification config. Add them when the heuristic proves too weak on real projects.
