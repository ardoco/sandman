# T2.6 Code elements from ArDoCo's code extraction (plugin `code-extractor-ardoco`)

Milestone M2 · Effort L · Depends on: T0.3, T0.10, T1.12 (done) · Blocks: T2.1b · User request 2026-10-10 (a); Q-19 (code extraction as a plugin)

Status: open · decided 2026-10-11: bracketed defaults; the ArDoCo plugin replaces the stub code extraction in e2e by default

## Context

Code files reach the KG only through the extraction plugin path (`config/extraction/plugins.yaml`, `match: {kinds: [code, test]}`). Today the regex stub `tests/plugin-stubs` answers. It emits file and class elements, `DEPENDS_ON` from imports and `REQ-n` references from comments. The user wants code elements from ArDoCo's own code extraction, so that ArDoCo SAD↔code (T2.1b) and the KG see the same code model. Read first:
- `docs/plugins.md` (contract, obligations, tokens), `contracts/skills.schema.json` (`PluginExtractInput`, `PluginExtractOutput`), `contracts/common.schema.json` (`ElementLocator`, `RelationType`), `contracts/kg/schema.yaml` (`Element`, `CodeUnit`, `TestCase`), `contracts/agent-cards/plugin-extract.template.json`
- `services/extraction-agent/src/sandman_extraction/extract.py` (`plugin_for`, element write: plugin `properties` are **not** stored; `match_references`), `tests/plugin-stubs/src/sandman_plugin_stubs/app.py` (reference plugin)
- `libs/java/agent-lib-a2a` (`A2aServer`: plugin mode with `SANDMAN_PLUGIN_INBOUND_TOKEN`), `services/tlr-agent` (Quarkus service layout, Dockerfile), `services/tlr-agent/approach-ardoco/pom.xml` (excluded Magika, onnxruntime, Eclipse JDT)
- `docs/tasks/T2.1-ardoco-tlr-adapter.md` open question 1, `docs/tasks/T2.5-corenlp-service.md`

Findings (ArDoCo `v2.1.0`, module `io.github.ardoco.tlr:model-provider`, package `edu.kit.kastel.mcse.ardoco.tlr.models`):
- **Entry points.** `CodeConfiguration(File, DIRECTORY | ACM_FILE, Metamodel)`. `DIRECTORY` uses `AllLanguagesExtractor(CodeItemRepository, path, Metamodel)` → `CodeModel`. `ACM_FILE` reads a written model (`CodeExtractor.readInCodeModel`). `CodeExtractor.writeOutCodeModel(model, file)` writes the ACM JSON (`codeModel.acm`, Jackson, `CodeModelDto`). The CLI `ardoco/code-model-extractor-cli` (`code <dir> <file>`) does the same with `Metamodel.CODE_WITH_COMPILATION_UNITS_AND_PACKAGES`.
- **Languages.** `AllLanguagesExtractor` runs `JavaExtractor` (Eclipse JDT `ASTParser`, bindings off) and `ShellExtractor`. Files are selected by Magika file-type prediction (`FileTypePredictor`, onnxruntime), not by suffix. ANTLR extractors for Java, Python 3 and C++ exist (`generators/antlr/...`, `AntlrExtractor`) but `CodeConfiguration` does not use them.
- **ACM items** (`core/api/models/code`): `CodeCompilationUnit` (file; `pathElements`, `extension`, `language`, `importedModuleNames`; `getPath()` = path relative to the extraction root), `CodePackage` (one per package segment), `ClassUnit` (classes and enums), `InterfaceUnit`, `ControlElement` (methods: name, start and end line, callee names; **no parameter types**), `Datatype` references (extends, implements). Classes and methods carry `startLine`/`endLine`. The JDT path sets no comments.
- **Ids.** `IdentifierProvider.createId()` is a JVM-global counter (`acm%09djsd`, starting at 1337). ACM ids depend on extraction order and earlier runs in the JVM. They are not stable across versions and must not be used as `localKey`.
- **Benchmark.** `ArDoCo/Benchmark` (HEAD `e60ddb2`) holds `*/model_*/code/codeModel.acm` and names the code commit in a README next to it: MediaStore `ArDoCo/MediaStore3@94c398f` (no licence stated), TeaStore `ArDoCo/TeaStore@bdc4902` (Apache-2.0). TeaStore's ACM has 205 compilation units (200 Java, 5 shell), 190 classes, 11 interfaces, 1137 methods, 1005 packages. These ACMs are from 2024 (older extractor, no line numbers). SAD↔code gold standards link sentences to files **and to directories** (TeaStore: 43 of 71 lines end with `/`).

## Goal

Code and test artifacts of a project get their KG elements from ArDoCo's code extraction. On a benchmark project, the element set equals ArDoCo's own code model of the same code. T2.1b can run ArDoCo SAD↔code on exactly the code model that ArDoCo would build.

## Decision: where it runs

A **Java plugin service `code-extractor-ardoco`** that speaks the existing A2A extract-plugin contract (`sandman.plugin.extract`), built on `agent-lib-a2a`.
- It reuses the plugin path of Q-19 and T0.10 without a contract change. An external code-extraction team can still replace it by configuration.
- The extraction-agent is Python, so ArDoCo cannot run in its process.
- In the tlr-agent, the code model would be built per TLR run and not exist in the KG, and the tlr-agent would need JDT, Magika and onnxruntime again (T2.1 removed them).
- JDT, Magika and onnxruntime return only in this module. The enforcer rule and ArchUnit keep them out of `approach-ardoco` and `tlr-agent`.

## Scope

1. **Module and service** `services/code-extractor-ardoco` (root `pom.xml` module, Quarkus like the tlr-agent). Dependency: `io.github.ardoco.tlr:model-provider:2.1.0` with LangChain4j excluded (open question 3). Agent Card from `plugin-extract.template.json`, `name` `code-extractor-ardoco`, `version` `2.1.0+c1` (raise `+cN` when the mapping changes). Plugin mode: `SANDMAN_PLUGIN_INBOUND_TOKEN_FILE`, `/healthz`, no KG access, no outbound calls, no LLM (`usesLlm` false).
2. **Staging.** Validate every `storagePath` (absolute, inside `/artifacts`, no symlink escape; reject otherwise with `INVALID_INPUT`, not retryable). Copy or hard-link `context.currentArtifacts` plus `artifacts` into a temp dir at their project `path`. Reject `..`, absolute paths and duplicate paths. Delete the temp dir after the call.
3. **Extraction.** Under one JVM lock: `IdentifierProvider.reset()`, then `new AllLanguagesExtractor(new CodeItemRepository(), dir, CODE_WITH_COMPILATION_UNITS_AND_PACKAGES).extractModel()`. Ids are then deterministic per input, but they are still not used as keys.
4. **Mapping** (only for the paths in `artifacts`; `label` = `CodeUnit` for kind `code`, `TestCase` for kind `test`):

   | ACM item | `kind` | `localKey` | `name` / `qualifiedName` | Lines | Parent |
   |---|---|---|---|---|---|
   | `CodeCompilationUnit` | `file` | `path` | file name / package + file name | – | – |
   | `ClassUnit`, `InterfaceUnit` | `type` (TestCase: `test-class`) | qualified name (nested: `Outer.Inner`) | simple / qualified name | yes | file or enclosing type |
   | `ControlElement` | `method` (TestCase: `test-method`) | type key + `#` + name, + `~n` for the n-th method of that name in source order (n ≥ 2) | name / type key `#` name | yes | type |

   `CodePackage` items are not elements, because an element belongs to one artifact version and a package spans files. The package is part of `qualifiedName`. `properties.typeKind` = `class | interface`, `properties.language` = ACM language. They are not stored today (open question 4). A compilation unit with no Java or shell content (Magika says otherwise) gives only the file element and a warning.
5. **Relations.** `DEPENDS_ON` from a type to the types it extends or implements, and from a file to the files of its resolved `importedModuleNames`, if the target is a current artifact of this plugin. No relations to unknown targets.
6. **Explicit references.** The JDT path has no comments. The plugin returns no `explicitReferences`. The extraction-agent applies its configured `explicitReferences.patterns` to plugin-routed files with `match_references` and the returned line ranges (small change in `extract.py`), so `REQ-n` in code still becomes a link (R-014 behavior of the stub).
7. **Limits.** Per call at most `SANDMAN_CODE_MAX_FILES` [20 000] staged files and `SANDMAN_CODE_MAX_BYTES` [500 MB]; above that, `INVALID_INPUT`, not retryable. `mem_limit` [3g] with `MaxRAMPercentage=75`; measure on TEAMMATES and set from the measurement. Timeout: the plugin entry's `timeout` [10m]. Out of memory or timeout returns `INTERNAL`, retryable.
8. **Second skill `sandman.plugin.code-model`** for T2.1b: input `{projectId, currentArtifacts[{path, storagePath}]}`, output `{acm: <ACM JSON as written by writeOutCodeModel>}`. Same staging, lock and extractor, so the ACM equals what ArDoCo builds in `DIRECTORY` mode. Additive schemas `PluginCodeModelInput`/`PluginCodeModelOutput` in `skills.schema.json` (contract PR first).
9. **Deploy.** Dockerfile (pinned base images, user 10001, no egress, Magika and JDT inside the jar, nothing downloaded at run time). Compose service on `internal` with `artifact-store:/artifacts:ro`, secrets `plugin_in_code-extractor-ardoco` and `svc_token_code-extractor-ardoco` (add the name to `PLUGINS` in `gen-secrets.sh`). `config/extraction/plugins.yaml`: the `code-extractor` entry points to `http://code-extractor-ardoco:8000`, token file `plugin_in_code-extractor-ardoco`. The stubs stay for the detect plugin and the contract tests. Add the component to `site/src/components.yaml` and `THIRD-PARTY.md` (ArDoCo MIT, Eclipse JDT EPL-2.0, Magika Apache-2.0, onnxruntime MIT). Update `docs/plugins.md` (reference plugins).
10. **e2e.** The mini fixture's code now goes through the ArDoCo plugin. Regenerate the golden with `replay-twice` in update mode. Accept only diffs in code and test elements, their relations, and links that depend on them; report the diff in the implementation notes.

Out: Python and C++ through the ANTLR extractors (open question 2); package or directory elements in the KG; T2.1b itself; incremental caching of the code model.

## Acceptance criteria

- Contract PR (`sandman.plugin.code-model` schemas) validates; the Agent Card validates against the template rules; `docs/plugins.md` lists the plugin.
- **Equivalence** (`CodeModelEquivalenceTest`, opt-in in CI by a `benchmark` profile, because it downloads): for TeaStore at `bdc4902`, the plugin's element set equals ArDoCo's own ACM of the same directory. ArDoCo's ACM comes from `AllLanguagesExtractor` 2.1.0 in a fresh run (the CLI path). Compared as sets of (kind, path, qualified name, start line, end line): every compilation unit, class, interface and method appears once on both sides. The test also reports, without failing, the diff against the Benchmark's committed `teastore/model_2022/code/codeModel.acm` (older extractor, by path and name). MediaStore runs in the same test.
- The `code-model` skill's ACM for TeaStore equals the ACM of `writeOutCodeModel` for the same directory, byte for byte, in two runs in one JVM (id reset works).
- Two calls with the same input give the same output (idempotent). `localKey`s of unchanged files stay the same after another file changes.
- A `storagePath` outside `/artifacts`, a symlink escape, `..` in `path` and the file and byte caps are rejected with `INVALID_INPUT`.
- The enforcer and ArchUnit fail if `approach-ardoco` or `tlr-agent` gets `org.eclipse.jdt`, `com.microsoft.onnxruntime` or `io.github.ardoco:magika`.
- TEAMMATES (fetched like TeaStore) extracts within `mem_limit` without OOM; the notes record peak heap, duration and file count.
- `make e2e` and CI stay green; e2e < 15 min; `replay-twice` identical.

## Open questions

1. Service per language or one service. [One service; `AllLanguagesExtractor` decides by Magika.]
2. Python and C++ through ArDoCo's ANTLR extractors. [Not in T2.6. `CodeConfiguration` does not use them, so ArDoCo's own runners would not see them either. Add them when an upstream runner does.]
3. LangChain4j: `model-provider` declares it. [Exclude it here; the code extractors do not load it. If a class fails to load, use the R-030 pattern: enforcer exception for this module plus an ArchUnit rule.]
4. Store plugin `properties` (`typeKind`, `language`) on the element. [Yes as a follow-up additive change: `Element.properties` as a JSON string, written like `references`. Not needed for T2.1b, which reads the ACM through the `code-model` skill.]
5. Method `localKey` without parameter types (the ACM has none). [`#name~n` in source order. A new overload before an existing one changes the later keys. Use JDT signatures directly only if this harms link history in practice.]
6. Packages and directories as elements (SAD↔code gold standards link to directories). [No elements. T2.1b maps a package or directory link to the file `CodeUnit`s below that path.]
7. Whole-project extraction on every call (cross-file relations need all current files). [Accept; cache the ACM by the sorted list of content hashes if ingest time matters (T5.4).]
