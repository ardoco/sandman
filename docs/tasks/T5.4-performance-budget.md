## Goal

The budget has numbers. One command measures them on a scratch stack. A failed item gets a fix or a recorded follow-up. ADR-0014 states whether Memgraph passed.

## Scope

1. The budget below.
2. The harness `scripts/perf.py` and `make perf`.
3. A measured run and its results in this file.
4. Fixes for failed items, if the fix is small and local.
5. `mem_limit` and heap changes in `deploy/docker-compose.yml`, only with measured evidence.
6. An ADR-0014 amendment.

Out: live LLM runs, LLM enrichment and LiSSA (no credentials, cost), multi-user load tests, Grafana dashboards, the 30-day soak test (T5.5).

## Host assumption

- Server with at least 8 cores and 32 GB RAM (A-7). Limits in `deploy/docker-compose.yml` assume this host.
- The measured run may use a smaller machine. The results section names the machine. A budget item that depends on memory is compared with the limits of the stack, not with the host.
- Time budgets assume that no other heavy process runs on the host.

### Per-unit budget (F-2, 2026-10-19)

Four time items grow with the number of documents, models and changed files, not with the file count alone. Their verdict is now per unit. The absolute limit stays in the table above as the reference at 1 000 files.

Assumptions of the reference workload (1 000 files, from the file mix above):

| Count | Value |
|---|---|
| Documents (architecture documents) | 200 |
| Models | 10 |
| Pairs (documents times models) | 2 000 |
| Changed files of ingest 2 | 100 |

| Id | Absolute limit | Unit | Per-unit limit |
|---|---|---|---|
| `ingest-e2e` | 900 s | document | 4.5 s |
| `ingest-tlr` | 480 s | document plus pair (2 200 units) | 0.218 s |
| `detection` | 120 s | pair | 0.06 s |
| `incremental-e2e` | 300 s | changed file | 3 s |

- The per-unit limit is the absolute limit divided by the count of the reference workload. The budget does not get looser.
- `perf.py` counts documents, models and pairs from the generated project and divides the measured value by them. A run with fewer files is judged by the same per-unit limit.
- An item passes if the per-unit value is at or below the per-unit limit. `result.json` and the table show both values.
- The run fails if a workflow does not end with the status SUCCEEDED, or if it times out.
- Fixed costs (debounce of 10 s, JVM and CoreNLP warm-up, step start) are part of the measured value. A small run has few units, so the fixed costs raise its per-unit value. A pass in a small run is a strong result. A fail in a small run needs a check of the fixed share before it is called a regression.
- The per-unit limits of `ingest-tlr` and `detection` assume a linear cost in pairs. Pair selection (a task after F-1b) can change that. Then set the unit again with a new amendment.

## Decisions taken

- Limits are recommended defaults. No earlier measurement exists. A later task may tighten them after the soak test (T5.5).
- The file count is one project of 1 000 files, because NFR-15 allows 5 000 files per project and the ingest cost is expected to grow linearly.
- Detection latency is the duration of the detection step, not the time to the first inconsistency, because the workflow runs detection after TLR in one pass.
- Query latency is measured over Bolt (engine, plan and transfer) and over HTTP (adds guard and authorization). The NL query path is dominated by the LLM call, which this task does not measure.
- The 200 000-node KG is built from copies of the benchmark data. The copies have the same shape and indexes as real data, but the properties of the nodes are synthetic (`seed_kg.py`).
- The 85 % limit leaves room for peaks that the 3 s sampling can miss.
- Memgraph passes if the six Memgraph items pass. The fallback (ArcadeDB, then Neo4j) is not started in that case.
- `stub-name-match` is off. It is a walking-skeleton stand-in and creates one link for almost every name match (228 621 links for 200 files, see Results). It would hide the real graph size.
- The harness uses the scratch project `sandman-perf`. It never touches `sandman` and its volumes.

## Harness

- `make perf` runs `scripts/perf.py`. Options: `PERF_ARGS="--files 1000 --delta 100 --kg-nodes 200000 --reps 3 --keep"`.
- The harness copies `config/`, switches enrichment and LiSSA off in the copy and mounts it in the five services that read it.
- It starts the services with `docker compose -p sandman-perf`, publishes Memgraph on `127.0.0.1:17687` and the query service on `127.0.0.1:18080`, and removes project and volumes at the end (unless `--keep`).
- It writes `.work/perf/result.json` (override with `--out`) and prints one table. The table adds one line per unit for the four time items. The exit code is 1 if an item fails or a workflow does not end with SUCCEEDED.
- Unit checks: `uv run pytest scripts/test_perf.py`.

### Memgraph

All six Memgraph items pass with a wide margin at the NFR-15 size. The first run had `stub-name-match` on. Ingest alone produced 2.92 million nodes and 8.82 million relationships (14 times the NFR-15 size). Memgraph used 3 410 MiB resident (peak 4 607 MiB), the Bolt p95 was 212 ms, the HTTP p95 was 1 743 ms, and the snapshot had 1 975 MiB. Memory and Bolt latency stay inside the budget at 14 times the size. The snapshot size and the HTTP latency do not.

### Findings

1. TLR and detection are the slow part, not extraction and not the KG. In the 1 000 file run, `ardocode` needs 7.3 s per document (200 documents, 1 460 s of the 1 935 s TLR step). `ArdocoRuns.LOCK` runs one ArDoCo pipeline at a time, and each run builds the code model of 700 code files again. The detector `ardoco-id` runs once per pair of document and model (about 2 000 pairs, 0.11 s each, 353 s in total). The cost grows with documents times models.
2. The synthetic mix has 200 architecture documents and 10 models. This is a stress case. A run with 200 files (8 documents, 2 models) passes the whole budget (ingest 187 s, TLR 123 s, detection 37 s, incremental 145 s).
3. An incremental ingest of 100 Java files takes as long as the full ingest (1 971 s against 2 329 s). The TLR step runs `ardocode` again for every document, because a code change can change every link.
4. `stub-name-match` creates 228 621 links for 200 files. It must stay off outside the walking skeleton.
5. The host has 18 GB, not 32 GB. The memory items do not depend on the host, because the stack uses about 5 GiB of its 27 GiB of limits.

No fix is small and local. A shorter run time needs a change of the ArDoCo run model (finding 1). The compose limits stay as they are: no container passed 60 % of its limit.

### F-1: ArDoCo cost per document

Run of 2026-10-18 on the same machine, `make perf PERF_ARGS="--files 1000 --delta 100 --kg-nodes 200000 --reps 3"`. All workflows ended with status SUCCEEDED.

| Id | Limit | Before | After F-1 | Verdict |
|---|---|---|---|---|
| `ingest-e2e` | 900 s | 2 329 s | 1 477 s | FAIL |
| `ingest-tlr` | 480 s | 1 935 s | 1 075 s | FAIL |
| `detection` | 120 s | 353 s | 360 s | FAIL |
| `incremental-e2e` | 300 s | 1 971 s | 799 s | FAIL |

All other items keep their verdict (pass). The run with 200 files: TLR step 123 s before, 94 s after. Incremental ingest 145 s before, 30 s after.

Changes (one commit each, results bit-identical, equivalence tests and TLR goldens stay green):

1. The code model of ArDoCo computed the endpoints and the type identifiers again for every word. Module `libs/java/ardoco-shadow` holds a same-name replacement of `CodeModelWithCompilationUnitsAndPackages` that computes them once. It returns copies. The adapter time of `ardocode` is 2.2 to 2.9 times lower in the unit measurement.
2. `ArdocoIdDetector` keeps the result of a pair of document and model. It skips the ArDoCo run if the document text, the model and the format are unchanged. A first ingest has no such pair. The incremental detection step fell from 345 s to 4 s.
3. `ArdocodeApproach` keeps the links of a document for the content address of the document and of the code model. It skips the run if both are unchanged.

Class loading: the replacement class has the same name as the ArDoCo class. `Model` is sealed, so both classes must load in one class loader. In tests, `%test.quarkus.class-loading.parent-first-artifacts` does this. In the image, `%prod.quarkus.class-loading.removed-resources` removes the original class from the ArDoCo jar. The first perf run without this removal showed no gain. A first version with parent-first loading in the image failed with `NoClassDefFoundError` for `CodeModel` and the `recover-trace-links` step failed. The harness does not fail the budget in that case. Check the workflow status in `result.json`.

Not done:

* Parallel runs. `ArdocoRuns.LOCK` stays. ArDoCo and CoreNLP keep JVM-wide state. Equal output cannot be shown without an audit of every singleton.
* Cache across restarts or replicas. All caches live in the memory of one JVM and start empty.

### F-1b: transarc cost per document

Profile of one `transarc` run on a synthetic project with 693 code files: 13 s. ArCoTL (SAM to code) uses about 65 % of it. `PathResemblance` with `CodeModel.getAllPackages` uses about 45 %. The text and model stages use 3.7 s.

Change (commit `perf: reuse transarc SAM-code links across documents of a model`):

* ArCoTL reads only the architecture model and the code model. It does not read the text. `TransarcApproach` now keeps the SAM to code links as pairs of item ids. The key is the approach version, the model format, the sha256 of the model file and the sha256 of the ACM. The cache is a bounded LRU (256 entries) in one JVM.
* On a hit, the informant builds `ArchitectureCodeTraceLink` objects again from the ids of the current run. If an id is unknown, it computes the links.
* The replacement of `SamCodeTraceabilityLinkRecovery` and `ArCoTLInformant` is a copy for ArDoCo 2.1.0 (`ponytail` comment in the code). `TransarcRunner` already copies `Transarc.definePipeline`. T3.7 must check both copies after an ArDoCo update. The shadow class of `ardoco-shadow` is not changed.
* `TransarcEquivalenceTest` runs every benchmark project twice: first without and then with the cache. Both runs equal standalone `Transarc`. The test passes for all five projects.

Run with `make perf PERF_ARGS="--files 200 --delta 20"` (8 documents, 2 models). All workflows ended with status SUCCEEDED.

| Id | Limit | After T2.7 | After F-1b |
|---|---|---|---|
| `ingest-e2e` | 900 s | 244 s | 193 s |
| `ingest-tlr` | 480 s | 181 s | 134 s |
| `detection` | 120 s | 38 s | 32 s |
| `incremental-e2e` | 300 s | 169 s | 124 s |

The run with 1 000 files did not end in the cap of 2 hours. It was stopped and the stack was removed. `perf.py` writes a result only at the end, so there is no partial result. The budget of the 1 000 file case is still unknown for `transarc`.

What the change cannot do:

* The cache saves ArCoTL for each model once per ACM. For 200 documents and 10 models it saves 1 990 of 2 000 ArCoTL runs. The text and model stages (about 3.7 s per pair) remain. They depend on the text and the model together.
* If any code file changes, the ACM hash changes and every model computes ArCoTL again (10 runs, not 2 000). The cost of the text and model stages per pair remains for every pair.
* `detection` is not changed. A cheaper pair needs a selection of pairs or a shared text annotation. Both can change results. Neither was done.

Next step: F-2. Count the budget per document and per pair, or measure the 1 000 file case with a longer cap. Share the parsed code model between runs only after a proof that ArDoCo does not change it (the ArCoTL steps are the only known readers).
