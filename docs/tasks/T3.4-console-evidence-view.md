# T3.4 Console evidence view (sentence text, model element, involved links, history)

Milestone M3 · Effort S · Depends on: T3.1, T0.9 (done) · Applies to `services/query-service`

Status: done (2026-10-17)

## Context

The console page `/console/inconsistencies/{id}` shows the finding, its involved elements and the status history. The page does not show what a reviewer needs to judge a finding of `ardoco-id`:
- The text of the sentence, the document and the position in the document.
- The model element and its current state.
- The trace links between the sentence and the model element.
- When the finding was first and last detected, and which artifact revisions are involved.

The owner API `GET /v1/inconsistencies/{id}` (inconsistency-agent) returns the involved elements, the involved trace links and the status history. It does not return the other trace links, the run times or the current state of the elements. The query-service has its own read path to the KG (`Reader`). T3.4 uses this path. T3.4 changes no contract.

## Goal

A reviewer sees the evidence of a finding on the detail page without a query. Missing or changed evidence is visible and does not break the page.

## Scope

1. A method `Service.evidence(project, detail)` in `services/query-service`. It runs read-only, parameterised Cypher with the `projectId` filter on `Service.reader`.
2. The console route `GET /console/inconsistencies/{id}` passes the result to the template. The route keeps the existing authorisation (`getInconsistency`, project read) and runs the queries only after this check.
3. A partial template `evidence.html`, included by `inconsistency.html`.
4. Tests in `services/query-service/tests`.

The page shows four blocks.

| Block | Content | Source |
|-------|---------|--------|
| Sentences and elements | Per involved element: kind, name, document path, section, sentence number (1-based), lines, text, state | Owner detail and current KG state |
| Trace links | Per link of an involved element: approach, confidence, status, active, both end names | `TraceLink` with `SOURCE` and `TARGET` |
| Detection | First and last detection (time, run, tool version), detection count, artifact revision at detection and now | `Run`, `DETECTED`, `ArtifactVersion`, `Ingestion` |
| History | Status changes as a timeline | Owner detail |

State of an involved element, compared with the current element of the same `key`:

| State | Condition |
|-------|-----------|
| `current` | A current element with this key exists and has the same `contentHash`. |
| `changed` | A current element with this key exists and has another `contentHash`. The page shows both texts. |
| `gone` | No current element has this key. |

Out: new owner endpoints, contract changes, a diff view, edit actions on links, a pagination of links.

## Decisions

| # | Question | Decision [default] |
|---|----------|--------------------|
| 1 | Where do the new data come from? | [The KG read path of the query-service.] The owner API stays unchanged. No contract change. |
| 2 | Which links are shown? | [All links with an end at an involved element, active links first, then by confidence. At most 30.] Links of old versions are shown as inactive. A cut list shows the note "more links exist". |
| 3 | What if the KG read fails? | [The page renders without the evidence blocks and shows a notice.] The triage form stays usable. |
| 4 | How is text escaped? | [Jinja autoescape only.] Text is shown in `<pre>`. No inline style and no script, because the CSP is `default-src 'self'`. |
| 5 | How long is the shown text? | [As stored: the element text is bounded to 4000 characters by the extractor.] |
| 6 | Which roles may see it? | [Every role that may call `getInconsistency` (viewer or higher).] The evidence is part of the same project. |

## Acceptance criteria

1. For a `missing-model-element` finding, the page shows the sentence text, the document path, the section, the sentence number and the trace links of the sentence.
2. For an `undocumented-model-element` finding, the page shows the model element, its document path and its trace links.
3. Each link row shows approach, confidence, status and active flag.
4. The detection block shows first and last detection and the detection count.
5. The state is `gone` if the element is no longer current, and `changed` if the content hash differs. Both cases render without error.
6. A text with HTML (`<script>`) appears escaped. The page has no script except the vendored htmx.
7. A user without read access to the project gets 404 for the page. The evidence queries run only after the check.
8. If the KG read fails, the page renders with a notice (HTTP 200).
9. `pytest` in `services/query-service` passes. Tests that need Memgraph run with Docker and skip without it.

## Test plan

Memgraph tests (Testcontainers, same seed pattern as `test_memgraph.py`): a sentence finding and a model finding with links of two approaches; an inactive link; a changed sentence; a removed element; a text with HTML; a project of another user. Fake-reader tests: the page renders when the KG read fails; no query runs for a user without access.
