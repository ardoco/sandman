# T1.7 Observability (OpenTelemetry, `obs` dashboards)

Milestone M1 · Effort S · Depends on: T0.11 (done) · Blocks: – (T1.5 provides real LLM token data for the dashboard)

## Context

NFR-7 asks for structured logs, distributed traces across A2A, event, KG and LLM calls, and LLM token tracking. Today only the plumbing exists: Python `sandman_agent.telemetry` sets up a `TracerProvider` with an OTLP/HTTP exporter when `OTEL_SDK_DISABLED=false`, adds `traceId`/`spanId` to JSON logs and injects `traceparent` into LLM requests and published events, but **no code creates spans** and the event consumer ignores `traceparent`. The Java libraries have no OpenTelemetry at all (`Event.create` always sets `traceparent = null`). Compose has the `obs` profile (`grafana/otel-lgtm:0.35.0`, Grafana via `edge-proxy` on `127.0.0.1:3001`) and passes `OTEL_SDK_DISABLED`/`OTEL_EXPORTER_OTLP_ENDPOINT` to agents. Read first:

- `docs/stage-2-contracts-repository.md` §1.7 (`OTEL_*`, log line fields), §3 (profiles, memory budget)

- Python: `libs/python/sandman-agent/src/sandman_agent/{telemetry,a2a,plugins,events,kg,llm}.py` (`_Executor`, `A2aClient`, `A2aPluginClient`, `EventPublisher`, `EventConsumer`/`handle_message`, `KgClient`, `OpenAiLlmClient`); services call `telemetry.setup_logging` in `__main__.py`
- Java: `libs/java/agent-lib/.../agent/{Event,EventPublisher,EventConsumer,KgClient,HttpPluginClient,MdcKeys}.java`, `libs/java/agent-lib-a2a/.../a2a/{SkillExecutor,A2aServer,A2aClient}.java`; Quarkus platform BOM 3.33.4 in the root `pom.xml`

## Goal

With `--profile obs` and `OTEL_SDK_DISABLED=false`, one walking-skeleton ingestion is visible in Grafana as one connected trace across query-service, extraction-agent, orchestrator, tlr-agent and inconsistency-agent, and three provisioned dashboards show A2A tasks, events and LLM tokens. With tracing disabled (the default) behavior and overhead are unchanged.

## Scope

1. **Python library.** Spans: A2A server task (`_Executor`; attributes agent, skill, task id, outcome), A2A client send and plugin calls (inject `traceparent` into the HTTP headers), event publish and consume (consumer continues the producer's context from the envelope `traceparent`), `KgClient` read/write/`write_tx` (`db.system = memgraph`, statement text, never parameters), `OpenAiLlmClient.chat/embed` (`gen_ai.*` request/response model, token usage). Metrics: add an OTLP `MeterProvider` next to the tracer; token usage and LLM call duration (`gen_ai.client.*`), A2A task duration by agent/skill/outcome, events published/consumed by type. All span/metric/attribute names are constants in `telemetry.py`.
2. **Java library.** Same spans and metrics in `agent-lib` (`opentelemetry-api` only, version from the Quarkus BOM): `EventPublisher` sets `traceparent` from the current context, `EventConsumer` extracts it, `KgClient` and `HttpPluginClient` spans, `SkillExecutor`/`A2aClient` spans in `agent-lib-a2a`. Services add `quarkus-opentelemetry` for HTTP server/client spans and OTLP export; `traceId`/`spanId` appear in the log MDC.
3. **Compose.** Java services get the Quarkus equivalents of `OTEL_SDK_DISABLED` and `OTEL_EXPORTER_OTLP_ENDPOINT` (open question 3); `.env.example` documents enabling `obs`.
4. **Dashboards** as Grafana JSON under `deploy/obs/dashboards/` (`a2a.json`, `events.json`, `llm-tokens.json`), provisioned into `otel-lgtm` by a read-only mount: A2A task rate/duration/failures per agent and skill; events published/consumed per type and consume latency; LLM tokens and calls per service, route and resolved model, plus error rate.

Out: Langfuse/Phoenix, gateway (Bifrost) spans, `llm-replay` spans (it already forwards `traceparent`), log shipping to Loki (open question 2), alerts (T1.10), the system overview dashboard (T1.9).

## Acceptance criteria

- Python and Java unit tests with in-memory span/metric exporters assert span names, parent/child links and attributes for: A2A server task, A2A client → server (same trace id across the HTTP hop), event publish → consume (same trace id through the envelope), KG statement (no parameter values in attributes), LLM call (token attributes and the token metric).
- A Java-published event carries a valid `traceparent` and still validates against `contracts/events.schema.json`; the cross-language interop test still passes.
- With `OTEL_SDK_DISABLED=true` no exporter is created and all existing tests pass without a collector.
- `docker compose --profile stubs --profile obs up` + walking skeleton: Tempo returns one trace containing spans of at least the five services named in the goal; the three dashboards load without errors in Grafana (manual check documented in the PR, or the optional smoke test below).
- `make test`, `make lint` green.

## Verification results (2026-10-09, implementation)

- Q3 Quarkus: `quarkus.otel.exporter.otlp.protocol` defaults to `grpc` (endpoint default `http://localhost:4317/`); the Quarkus guide documents only `quarkus.otel.*` (env `QUARKUS_OTEL_*`), standard `OTEL_*` variables are not read. Services set `quarkus.otel.sdk.disabled=true` and protocol `http/protobuf` in `application.properties`; compose passes `QUARKUS_OTEL_SDK_DISABLED` (empty, i.e. default disabled, unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set) and `QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT`. Quarkus metrics need `quarkus.otel.metrics.enabled=true`. Checked live in the `obs` stack (spans of tlr-agent and inconsistency-agent arrive in Tempo).
- Q4 otel-lgtm 0.35.0: Grafana provisioning goes through `/otel-lgtm/grafana/conf/provisioning/dashboards/` (provider YAML plus dashboard folder, documented in grafana/docker-otel-lgtm). Compose mounts `deploy/obs/dashboards.yaml` and `deploy/obs/dashboards/` read-only there; the three dashboards load (uids `sandman-a2a`, `sandman-events`, `sandman-llm-tokens`).
- Q5 / V-14 GenAI conventions moved to `open-telemetry/semantic-conventions-genai` (status Development, no release tag yet). Pinned in `telemetry.py`: span `{gen_ai.operation.name} {gen_ai.request.model}` with `gen_ai.operation.name` = `chat`/`embeddings`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`/`output_tokens`. The metric names in the task text (`gen_ai.client.token.usage`, `gen_ai.client.operation.duration`) are superseded there by `gen_ai.client.inference.usage.input_tokens`/`output_tokens` (counters, `{token}`) and `gen_ai.client.inference.duration` (histogram, `s`); those are used. The attribute `gen_ai.system` is replaced by `gen_ai.provider.name`.

## Implementation notes and deviations

- DB spans use `db.system.name` / `db.query.text` (current semconv) instead of `db.system`.
- No `opentelemetry-instrumentation-fastapi`: the installed FastAPI has native OpenTelemetry (server spans, W3C extraction). Services pass `telemetry=FASTAPI_TELEMETRY` (`auto_configure=False`, so the library's providers are used; without it FastAPI installs its own provider without service name). Only `opentelemetry-instrumentation-httpx` was added on the Python side.
- Telemetry is on only with `OTEL_SDK_DISABLED=false` and an OTLP endpoint (`telemetry.enabled()`).
- The orchestrator stores the current `traceparent` per step (migration `002_step_traceparent.sql`) and submits the step inside a `workflow.step` span continuing it, so a pipeline stays one trace although steps start from the tick loop.
- Java: `Telemetry` (agent-lib) gets the OpenTelemetry instance from the Quarkus bean via `TelemetryBridge` (agent-lib-a2a), otherwise the global one (no-op). `quarkus-logging-json` added to both Java services (keys `ts`, `msg`, `service`, flat MDC); disabled in `%test`/`%dev`.
- Java has no LLM client yet, so no Java `gen_ai.*` spans. The dashboard service is not instrumented (separate work stream).
