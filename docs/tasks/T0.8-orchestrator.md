# T0.8 Orchestrator

Milestone M0 · Effort L · Depends on: T0.2 · Blocks: T0.11

## Context

The orchestrator (Python) consumes events from NATS JetStream, maps them to A2A skill calls via a rule table, tracks workflows in SQLite and handles retries/timeouts. Events are the only signal it chains steps on: a step completes when its completion event (`causationid` = `messageId` of the A2A request) arrives; `GetTask` polling only detects failures (ADR-0003/0006 amendments). It does not write to the KG. Its M0 version is close to final; only the optional LLM planner (M6) is missing. Read first:
- `docs/stage-1-analysis-architecture.md` §3.2 (event delivery), §3.4 (sequence diagrams, failure handling), §6 (rules, concurrency, human in the loop)
- `adr/0003-nats-jetstream-event-bus.md`, `adr/0006-rule-based-orchestration.md`
- `docs/stage-2-contracts-repository.md` §1.3, §1.4 (stream/consumer config), §1.6 (`rules.yaml`), §4.1
- `contracts/openapi/orchestrator.yaml`, `contracts/events.schema.json`, `contracts/skills.schema.json`, `contracts/agent-cards/*.json`

## Goal

`services/orchestrator` (package `sandman_orchestrator`): FastAPI app with the REST API, a background event consumer and a step executor.

## Scope

1. SQLite schema: `inbox(event_id PK, type, project_id, payload, received_at, processed_at)`, `workflows`, `steps(id, workflow_id, agent, skill, input_json, action_key, status, attempts, a2a_task_id, result_json, error_json, started_at, ended_at, next_attempt_at)`, `dead_events`. Migrations as plain SQL files.
2. Consumer: durable `orchestrator` (Stage 2 §1.4); insert into `inbox` (duplicate id → ack and skip); ack only after the insert commits; events that fail permanently → `dead_events`.
3. Rule engine per `config/orchestrator/rules.yaml` and Stage 1 §6: completion events (`causationid` matches the `messageId` of any attempt of a running step; the orchestrator generates and stores the `messageId` before `SendMessage`, so a fast event can never arrive unmatched) → step `SUCCEEDED` with the event data as result, then the rules; `ingestion.completed` → extract created ∪ reactivated versions (or detect with `scopeArtifactIds` = deleted artifacts when only deletions); `extraction.completed` → debounced TLR over changed × counterpart current versions for the configured kind pairs, or detection on the extracted artifacts if no kind pair applies; `tracelinks.updated` → debounced detection with `scopeArtifactIds` = artifacts of the source and target versions; `inconsistencies.updated` → close workflow; `inconsistency.status.changed` → audit log. Current versions and version → artifact ids are fetched read-only from the KG (the only KG access, via `KgClient.read`). Correlation: workflow id propagates via `correlationid` and `sandman.workflowId`.
4. Executor: **per project at most one running step** (pipeline lock: extract → tlr → detect never overlap); coalesce pending triggers (union of version/artifact ids); per-agent concurrency limit; `actionKey` = sha256(JCS(agent, skill, input, triggerId)) with triggerId = triggering event id or manual request id (duplicates of the same trigger are suppressed; a later trigger with identical input runs again); A2A submit with the orchestrator's own token and, for manual triggers, `sandman.actor` = the forwarded user; `GetTask` polling with backoff (30 s → 2 min) only to detect `FAILED`/`REJECTED`/`CANCELED`/task-not-found (a `COMPLETED` poll result does not complete the step); timeouts → `CancelTask`; retry policy (`REJECTED` no retry; `FAILED` with `retryable`, connection errors, task-not-found → retry up to `maxAttempts`); `BUDGET_EXCEEDED` → step `BLOCKED`.
5. Recovery on startup: resume polling for `RUNNING` steps from the stored task ids; their completion events are redelivered by JetStream if not yet acked.
6. REST per `contracts/openapi/orchestrator.yaml` (list/get/create/cancel workflows, dead events + replay); manual workflow types `full`, `extract`, `tlr`, `detect`.
7. Default `config/orchestrator/rules.yaml` for the walking skeleton.

Out: LLM planner, approval gate (M6), scheduled prune (M5).

## Acceptance criteria

- Rule unit tests: for each event type the expected steps/inputs are produced; debounce merges three `extraction.completed` events within the window into one TLR step; a completion event completes exactly the step with the matching task id; no step of a project starts while another step of the project runs.
- Executor tests with a fake A2A agent (in-process ASGI app built with `sandman_agent.a2a.serve`): success; `REJECTED` without retry; retryable failure with retries then `FAILED`; task-not-found after a simulated agent restart triggers a retry; timeout triggers `CancelTask`; identical trigger twice → one step; `force` → two steps.
- Restart test: kill the orchestrator with a `RUNNING` step, restart it, and the step completes. Unacked events are redelivered and processed exactly once (inbox).
- The REST API passes Schemathesis against `contracts/openapi/orchestrator.yaml`.

## Constraints

Python 3.13, `sandman_agent`, FastAPI, stdlib `sqlite3` (or `aiosqlite`); no workflow engines or agent frameworks. Single process, asyncio.
