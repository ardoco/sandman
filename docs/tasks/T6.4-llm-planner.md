# T6.4 LLM planner with approval gate

Milestone M6 · Effort L · Depends on: M5 · Risk: RK-9 (injection into LLM prompts)

Status: planned. Optional task. Rule-based orchestration stays the default.

## Context

ADR-0006 chose a hybrid. Rules handle events. An LLM planner handles only natural-language user requests and outputs a validated plan. A plan needs user approval first.
The orchestrator already has the stubs `POST /v1/requests` and `POST /v1/workflows/{workflowId}/approval`. Both answer 501.

Read first:
- `adr/0006-rule-based-orchestration.md` (plan validated against skill schemas, workflow `BLOCKED` until approval)
- `adr/0013-users-and-roles.md` (roles are checked in the query-service; owners get `X-Sandman-Actor`)
- `docs/tasks/T7.5-resolution-suggestions.md` (pattern: flag, schema, fence, record, authorize before flag)
- `services/orchestrator/src/sandman_orchestrator/rules.py` (`manual`, `SKILL_AGENT`)
- `services/query-service/src/sandman_query/suggest.py` (prompt fence and schema validation)

## Goal

A maintainer writes a goal, for example "check the docs of component X against the code". The orchestrator asks the LLM for a plan. The plan holds a bounded list of known step types. A valid plan waits as a `BLOCKED` workflow. A maintainer approves or rejects it. Only an approved plan runs, exactly once.

## Design

| Item | Decision |
| --- | --- |
| Flag | `planner.enabled` in `config/orchestrator/rules.yaml`. Default `false`. A disabled flag answers 501. |
| Other settings | `planner.maxSteps` (default 5, maximum 10) and `planner.approvalTtl` (default `24h`). |
| Step catalog | `extract`, `tlr`, `detect`, `derive`. These are the non-destructive kinds of `manual()`. `prune` and plugin skills are not in the catalog. |
| Plan | JSON `{"steps": [{"type", "params", "rationale"}]}`. The schema forbids unknown fields. `params` allows only `options` (extract), `approaches` (tlr), `scopeArtifactIds` and `detectors` (detect). |
| Expansion | The orchestrator expands each step with `manual()`. Version ids come from the KG, never from the LLM. The planner cannot set `projectId` or version ids. |
| Validation | Every expanded step input is validated against `skills.schema.json` (`<Skill>Input`). Any error rejects the whole plan (400 with the error list). A plan with zero steps, more than `maxSteps` steps or a step that expands to nothing is rejected. |
| Storage | One workflow with `trigger.kind` `planner`. Its steps are `BLOCKED`. A row in the new table `plans` holds goal, plan, model, route, `promptHash`, requester, expiry and the approval state. |
| Approval | `POST /v1/workflows/{id}/approval`. `approve` moves the `BLOCKED` steps to `PENDING` in one transaction that also sets the state `APPROVED`. A second decision answers 409. |
| Rejection | `reject` sets the state `REJECTED` and cancels the steps. |
| Expiry | After `approvalTtl` the state becomes `EXPIRED` and the steps are canceled. The executor sweeps expired plans. An approval after expiry answers 409. |
| Roles | The query-service forwards `POST /v1/projects/{projectId}/requests` (`maintainer`) and `POST /v1/workflows/{workflowId}/approval` (`maintainer` on the project of the workflow). The orchestrator accepts both calls from the query-service only. Approval needs a user actor. |
| Check order | Authorization first, then the flag (T7.5 lesson). A caller without access gets 403 or 404, never 501. |
| Prompt | One system prompt and one user message. The goal sits between `<goal>` and `</goal>` as JSON. The characters `<` and `>` are escaped. The system prompt says to ignore instructions in the goal. |
| Recording | Model (resolved by the gateway), route, SHA-256 of prompt and schema (`promptHash`), requester, approver, times. |
| Execution | An approved plan runs as ordinary steps (per-project lock, retries, timeouts). The approver is the actor of the A2A calls. Event follow-up rules do not add steps to a planner workflow. |
| Retry guard | `POST .../retry` must not resume a plan that waits for approval. |
| LLM access | `ModelSelector` and the project `llmPolicy`, as in the extraction-agent. Settings `SANDMAN_LLM_*` already exist for the orchestrator. |

## Scope

In:
1. Module `planner.py`: prompt, schema, validation, prompt hash.
2. Migration `005_plans.sql`, orchestrator methods for create, decide and expire.
3. Orchestrator routes (replace the 501 stubs), config schema entry, OpenAPI entries.
4. Query-service forwarding routes with role checks, OpenAPI entries.
5. Offline tests with a scripted LLM client. User docs.

Out:
- Step dependencies and data flow between steps. Steps are independent and run in order per project.
- Plans that change artifacts, prune data or call plugin skills.
- Console page for requests. The API and the CLI-style HTTP call are enough for the first version.
- Re-planning, multi-turn dialog, streaming.
- Four-eyes rule. The requester may approve own plan.

## Acceptance criteria

1. With the flag off, `POST /v1/requests` answers 501 and no LLM call happens.
2. A caller without the role gets 403 or 404 before the flag is checked.
3. A plan with an unknown step type, an unknown param, a reserved param (`projectId`, version ids) or invalid skill input is rejected and stores nothing.
4. A plan with more than `maxSteps` steps or with no steps is rejected.
5. Goal text that tries to close the fence stays inside it.
6. A valid plan creates a `BLOCKED` workflow. No step starts without approval, also after `retry` and after an executor tick.
7. Approval runs every step exactly once. A repeated approval answers 409.
8. Rejection and expiry cancel the steps. An approval after either answers 409.
9. The record holds model, `promptHash`, requester and approver.
10. With the flag off, event rules and manual workflows behave as before.
11. `make contracts`, `ruff` and `uv run pytest services/orchestrator services/query-service` are green.

## Test plan

- Scripted LLM client (`ScriptedLlmClient`): no live LLM.
- Orchestrator tests: flag off, schema errors, reserved params, step bound, injection text, approve once, unapproved never runs, reject, expiry, retry guard, record fields, actor.
- Query-service tests: authorization matrix entries for both operations, forwarding with the actor, authorize-before-flag.

## Risks

- RK-9: goal text is user input, but it can contain text from pasted artifacts. Mitigation: fence, escape, schema, catalog allowlist, ids from the KG, approval gate.
- Strict JSON schema mode of the gateway may reject the open `params` object. Local validation is the enforcement. A live check is open.
- Version ids are resolved at plan time. An ingestion between plan and approval makes the plan stale. The approval TTL limits this.
- The dashboard alert for BLOCKED workflows also counts plans that wait for approval.
- Cost: one LLM call per request, off by default, under the gateway budget.
