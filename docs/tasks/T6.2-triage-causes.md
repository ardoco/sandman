## Context

A triager moves an inconsistency to ACCEPTED, REJECTED or DEFERRED with a free-text `reason` (ADR-0007). Free text does not tell why a finding is wrong or right. For analysis, somebody must code each reason by hand.

The paper names this problem. Sandman must tell extraction errors from genuine inconsistencies. Some inconsistencies are planned, for example during a migration (paper §4, challenge 4, p. 490). See `docs/notes/paper-review-3774748.3795871.md` §3.2.

## Goal

Each user transition to ACCEPTED, REJECTED or DEFERRED carries a cause from a fixed list. Exports and analyses use the cause without manual coding.

## Scope

In:
1. A cause enum in `contracts/common.schema.json`.
2. An optional `cause` field on the transition request, `StatusChange`, the history entry and the status event.
3. Validation in the inconsistency-agent.
4. A required cause select in the console.
5. A cause column in the inconsistency export.

Out:
- Causes for system transitions (`re-detected`, `not-redetected`, `artifact-deleted`). These keep their `reason` only.
- Automatic cause prediction (T7.5 may propose one later).
- Migration of old free-text reasons. Old entries have no cause.

## Cause list

| Value | Meaning | Typical target status |
|---|---|---|
| `extraction-error` | An extractor produced a wrong or missing element. | REJECTED |
| `link-error` | A trace link is wrong or missing. | REJECTED |
| `detector-error` | The detector is wrong although its inputs are correct. | REJECTED |
| `artifact-inconsistency` | The artifacts really disagree. Somebody must fix an artifact. | ACCEPTED |
| `planned-change` | The artifacts disagree on purpose because of a known future architecture change. | ACCEPTED, DEFERRED |
| `intentional` | The disagreement is intended and stays, for example an abstraction in the documentation. | REJECTED, ACCEPTED |

The table gives typical pairs only. The agent does not restrict the combination of cause and status.

## Contract changes

Make the contract change in its own PR first (plan §2, general rules). The change is additive.

1. `contracts/common.schema.json`: add `$defs/TriageCause` with the six values above.
2. `contracts/openapi/inconsistency-agent.yaml`:
   - `transitionInconsistency` body: add optional `cause` (`TriageCause`).
   - `InconsistencyDetail.history` items: add optional `cause`.
   - 422 description: add "cause given for a transition to OPEN".
3. `contracts/kg/schema.yaml`: add optional `StatusChange.cause`. Bump the minor version.
4. `contracts/events.schema.json`: add optional `cause` to `InconsistencyStatusChanged`.
5. The export (`exportInconsistencies`): the JSON format carries `cause` through `InconsistencyDetail`. Add the column `cause` to the CSV format.

## Behavior

1. The API accepts a transition without `cause`. Old clients keep working.
2. If `cause` is present and `to` is OPEN, the agent answers 422.
3. The agent stores `cause` on the `StatusChange` node and copies it into the event.
4. The console shows a required select for ACCEPTED, REJECTED and DEFERRED. The select has no default value. The `reason` text stays required as before.
5. A user transition to RESOLVED may carry a cause. The console shows an optional select for RESOLVED.
6. The console history shows the cause next to the reason.

## Decisions taken

| Id | Question | Decision |
|---|---|---|
| D-1 | Required in the API? | No. Required in the console only (PR-D6). Scripts and old clients keep working. |
| D-2 | Fixed list or free tags? | Fixed list. Analyses need stable values. A new value is an additive contract change. |
| D-3 | Separate `planned-change` from `intentional`? | Yes. A planned change ends; an intentional deviation stays. Temporal analyses (T7.4) need this difference. |
| D-4 | Restrict cause per status? | No. The table shows typical pairs only. A restriction would block valid edge cases. |
