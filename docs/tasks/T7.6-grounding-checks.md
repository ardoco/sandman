# T7.6 Grounding checks

Milestone M7 · Effort S · Depends on: M4 · Risk: RK-9 (injection into LLM output)

Status: done (2026-11-06).

## Context

LLM output must not add facts that point at nothing. Three paths exist today:

| Path | Check today |
| --- | --- |
| Answer synthesis, `graphrag`, `explore` (query-service) | Citations must be ids of the result rows or the evidence (R-032). Already enforced. |
| Enrichment (extraction-agent) | The prompt holds no ids. Mentions use ids that the service selected. No LLM-cited id exists. |
| TLR approaches that use an LLM (tlr-agent) | `RecoverTraceLinks` passes `CandidateLink` ids to `LinkStore.writeInactive`. The Cypher `MATCH` drops an unknown id without a trace. |

Each trace link is produced by one approach. A user cannot see how many approaches agree on a pair. The console Links page shows this count only per element pair.

Read first:
- `contracts/kg/schema.yaml` (`TraceLink`)
- `services/tlr-agent/src/main/java/edu/kit/kastel/mcse/ardoco/sandman/tlr/RecoverTraceLinks.java` (`runApproach`)
- `services/query-service/src/sandman_query/query.py` (`TRACELINKS`), `console.py` (`link_pairs`)

## Goal

1. A candidate link whose source or target is not an element of the run input is rejected, counted and logged.
2. The trace-link export shows `agreementCount`: the number of distinct approaches that produced an active link for the same element pair.

## Scope

In:
1. Grounding filter in `RecoverTraceLinks` before `writeInactive`.
2. `agreementCount` in the JSON export and in the CSV export (query-service).
3. Tests for both.

Out:
- New KG properties. `agreementCount` is computed on read, so it cannot become stale.
- Changes to the query-service citation checks (they exist).
- Enrichment checks (no LLM-cited ids exist).
- Rejected links count as an approach (the export hides them unless `includeRejected` is set; the count uses the rows that the query returns).

## Contract changes

Additive. `contracts/openapi/query-service.yaml`, route `exportTraceLinks`: JSON member `agreementCount` (integer, at least 1, optional) and CSV column `agreement_count` at the end.
The skill output stays the same (`additionalProperties: false`), so the rejected count goes to the log only.

## Behavior

- Ground rule: the element ids of `TlrInput.sources` and `TlrInput.targets` are the only ids a candidate may use. This covers pairwise and whole-project input. The source id must be a source element and the target id a target element.
- A rejected candidate is not written. The run logs one warning with the approach id and the count.
- `agreementCount` = number of distinct `approach` values among the returned links with the same `sourceKey` and `targetKey`. All links of the pair carry the same count.

## Acceptance criteria

- A candidate with an unknown source or target id is not written; a valid candidate in the same run is written.
- The JSON export of two approaches for one pair shows `agreementCount` 2 on both rows; a single link shows 1.
- The CSV header ends with `agreement_count`.
- `uv run pytest services/query-service` narrow tests, ruff and the Java unit test of the filter are green.

## Test plan

- Java unit test of the filter (no KG, no Docker).
- Python test of the count with the fake reader (`tests/test_query.py` pattern).
