## Context

Sandman stores versions, elements, trace links and code dependencies. After a push, a developer cannot ask: "Which documentation must I check because of this change?" The data for the answer is in the KG, but no feature uses it.

The paper names change impact analysis as a use of the knowledge base (paper §3.2, p. 489). It also names outdated information as a consistency problem (paper §3.3, p. 489). See `docs/notes/paper-review-3774748.3795871.md` §3.3.

## Goal

For one ingestion, Sandman lists the changed elements and the elements in other artifacts that they affect. Each affected element has the path that connects it to a change. The report is in the API, the console and the GitHub Action job summary.

## Scope

In:
1. A read-only impact computation in the query-service.
2. The endpoint `GET /v1/projects/{projectId}/ingestions/{ingestionId}/impact`.
3. A console page.
4. A CLI command and a Markdown job summary in the Action.

Out:
- LLM ranking or explanation of the impact (PR-D7).
- Impact across projects.
- Impact of changes that did not come through an ingestion.
- Rename detection (backlog B-5). A renamed element counts as one deleted and one added element.

## Definitions

- **Ingestion version pair**: for each artifact that the ingestion activated, the new version is the version on the `ACTIVATED` edge of this ingestion. The old version is the version on the latest `ACTIVATED` edge of an earlier ingestion (lower `seq`) for the same artifact. If no old version exists, the artifact is new.
- **Changed element**: an element of the new version whose `key` has no element in the old version (added), or whose `contentHash` differs (modified). An element of the old version whose `key` has no element in the new version is removed. A deleted artifact (`DELETED` edge) makes all elements of its last version removed.
- **Affected element**: an element of a current version in a different artifact. It is reachable from a changed element within the depth limit over these edges:
  - active `TraceLink` with `status <> 'rejected'`, in both directions
  - `DEPENDS_ON`, in both directions
  - `CONTAINS`, upward only, to report the enclosing section or type
- **Depth**: number of edges on the path. Default 2, maximum 4.

For a removed element, use the links of the old version. These links are inactive now, so the traversal reads them from the old version on purpose. Mark these paths with `via: previous-version`.

## API

Contract change in its own PR first (plan §2, general rules). The change is additive.

`GET /v1/projects/{projectId}/ingestions/{ingestionId}/impact`
- Minimum role: `viewer`. Project scope check as for all project routes.
- Query parameters: `depth` (1 to 4, default 2), `limit` (1 to 1000, default 200).
- Response 200 (JSON):
  - `ingestionId`, `seq`, `sourceRevision`, `workflowStatus`
  - `complete` (boolean): false while the workflow of the ingestion runs. Links may be missing then.
  - `changed`: list of `{key, artifactPath, label, kind, change: added | modified | removed}`
  - `affected`: list of `{key, artifactPath, label, kind, name, excerpt, distance, paths}`. `paths` holds at most 3 shortest paths. A path is a list of `{key, edge}`.
  - `truncated` (boolean)
- Order of `affected`: distance, then artifact path, then key.
- Responses 404 (unknown ingestion or other project) and 400 (bad parameter).

Run all reads in one read transaction with a timeout. Use parameterized Cypher with `projectId` in every `MATCH` (RK-10). The query-service owns this code; no agent changes.

## Console, CLI and Action

1. Console page `impact.html`: changed elements, then affected elements grouped by artifact. Each element links to its detail. Show a banner while `complete` is false.
2. CLI: `sandman impact <ingestionId> [--depth N] [--format json|markdown]`.
3. Action: new input `impact-summary` (default `true`). If `wait` is true and the workflow succeeded, the Action writes the Markdown report to `$GITHUB_STEP_SUMMARY`. The summary lists at most 50 affected elements and a link to the console page.

## Decisions taken

| Id | Question | Decision |
|---|---|---|
| D-1 | LLM in the report? | No (PR-D7). The report is a deterministic graph traversal. |
| D-2 | Which edges? | Active non-rejected trace links, `DEPENDS_ON` in both directions, `CONTAINS` upward. Other edges add noise. |
| D-3 | Default depth | 2. Depth 1 misses documentation of a dependent component. Depth 3 and more grow fast on code. |
| D-4 | Report elements in the same artifact? | No. The author of a change already looks at the changed artifact. |
| D-5 | Store the report? | No. Compute on request. The KG keeps the versions until retention removes them. |
| D-6 | Old version removed by retention? | Answer 200 with `changed` based on available data and a `warnings` entry. Do not fail. |

## Acceptance criteria

1. Contract PR merged first. Conformance vectors are green.
2. Unit tests for the change set: added, modified, removed, new artifact, deleted artifact.
3. Memgraph integration test on a fixed graph:
   - one modified sentence linked to a model element; the model element linked to a second document: the second document's sentence appears at distance 2 with its path
   - a rejected link does not create a path
   - an element in the same artifact does not appear
   - depth 1 hides the distance-2 element
4. Security test: an ingestion id of another project answers 404. The traversal never leaves the project (T4.4 suite pattern).
5. End-to-end test: two ingestions of a benchmark project with one changed Java class. The report lists the linked documentation sections.
6. Performance: on the T5.4 workload (ingest 2), the endpoint answers in less than 2 s at depth 2. Met on the 200 file workload (see Performance result).
7. Action test: with `wait: true`, the job summary contains the report heading and at most 50 rows.

Shared constraints of plan §5 apply. The feature is read-only.

## Performance result

Run of 2026-10-20 with `make perf PERF_ARGS="--files 200 --delta 20"` (40 documents, 2 models). The harness has the new budget item `impact-depth2` (limit 2 s). It calls the endpoint with `depth=2` three times and judges the slowest call. All workflows ended with status SUCCEEDED. Machine as in the T5.4 results. Result file: `.work/perf/result.json` (not committed).

| Ingestion | Changed | Affected | Truncated | Median | Slowest | Limit | Verdict |
|---|---|---|---|---|---|---|---|
| Ingest 2 (20 changed Java classes) | 20 | 7 | no | 0.033 s | 0.063 s | 2 s | pass |
| Ingest 1 (all elements new, worst case) | 1 000 | 58 | yes | 0.841 s | 1.032 s | 2 s | pass |

- The old edit of ingest 2 (a comment line) changed no element, so the report was empty. A method body edit also changed no element, because the hash of a code unit does not cover method bodies. The harness now appends one method to each changed class.
- The run has 20 changed files, not 100, and 200 files, not 1 000. Ingest 1 reaches the cap of 1 000 changed elements, so it bounds the cost of a large change.
- The 1 000 file value is not measured. Repeat the run when the 1 000 file workload ends (T5.4 follow-up F-3).
- No fix was needed.
