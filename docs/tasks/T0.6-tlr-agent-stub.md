# T0.6 TLR-agent stub

Milestone M0 · Effort M · Depends on: T0.3 · Blocks: T0.11, M2

## Context

The tlr-agent (Java, Quarkus) runs pluggable trace link recovery approaches and owns `TraceLink` nodes (except explicit references). ArDoCo and LiSSA approaches come in M2. In M0 a trivial approach exercises the full path. Read first:
- `docs/stage-1-analysis-architecture.md` §4 (TraceLink, Run, ids), §5.3
- `docs/stage-2-contracts-repository.md` §1.3 (A2A convention), §1.6 (`config/tlr/approaches.yaml`), §4.3
- `adr/0012-pluggable-approaches-and-detectors.md`
- `contracts/agent-cards/tlr-agent.json`, `contracts/openapi/tlr-agent.yaml`, `contracts/skills.schema.json` (`RecoverTraceLinks*`, `ListApproachesOutput`), `contracts/events.schema.json` (`TracelinksUpdated`)

## Goal

`services/tlr-agent`: Quarkus app with the A2A skill `recover-trace-links`, REST `GET /v1/approaches`, health endpoints, and the approach SPI with one stub approach.

## Scope

1. SPI `TraceLinkApproach { String id(); String version(); Set<KindPair> supports(); List<CandidateLink> recover(TlrInput in, TlrContext ctx); }`, discovered via `ServiceLoader`, enabled and parameterized by `config/tlr/approaches.yaml`. `configHash` = sha256 of the JCS of the approach's effective params.
2. `TlrInput`: source/target elements of the given versions, loaded once from the KG (id, key, label, kind, name, text, artifact kind; `ORDER BY` key). `TlrContext`: `LlmAccess` for the project policy, `ArtifactStore`, cancellation flag, logger.
3. Approach `stub-name-match` (Stage 2 §4.3) for all kind pairs.
4. Skill handling: validate input; select approaches (input list or `config/orchestrator`-independent defaults: all enabled approaches supporting the kind pairs of the given versions); per approach: `RunRecorder.cleanupStale(inputKey)`, `start`, recover, write links in batches of 5 000 with `active=false` (Stage 1 §4.4; deterministic link ids), then one final transaction that deactivates the approach's earlier active links between the given source and target versions that this run did not produce, activates the links this run `PRODUCED` (also pre-existing ids) and completes the `Run`; failures of one approach → its run `failed`, others continue; return `SkillResult` with `RecoverTraceLinksOutput` and **one** `sandman.tracelinks.updated` event listing all runs.
4a. At startup, deactivate active links of approaches that are disabled in `config/tlr/approaches.yaml`.
5. `GET /v1/approaches` per `ListApproachesOutput`.
6. Default `config/tlr/approaches.yaml` for the walking skeleton.

Out: ArDoCo/LiSSA (M2), link carry-over, link review.

## Acceptance criteria

- `@QuarkusTest` + Testcontainers: on a seeded KG (Requirement "Cache media files", CodeUnit `MediaCache`, CodeUnit `UserDB`), the skill creates exactly one active link with the expected deterministic id, a `Run` with `tool=stub-name-match`, and publishes one valid `sandman.tracelinks.updated` event with `causationid` = `messageId` of the A2A request.
- Running the same input twice yields no duplicate links. The same input run again (new run, identical link ids) leaves those links active. A rerun with changed approach params (new `configHash`) leaves exactly the new links active. Links of an interrupted run (killed before the final transaction) are never active. A failing test approach (registered only in tests) yields `status=failed` for it while the stub approach completes.
- Skill results, events and the `/v1/approaches` response validate against the contracts. The A2A conformance cases pass through the real Quarkus endpoint.
- The enforcer still bans LangChain4j in this module (ArDoCo/LiSSA adapter packages are added in M2 with an explicit exception).

## Constraints

Java 21, `agent-lib` + `agent-lib-a2a`; no agent frameworks; no LLM calls in the stub approach.
