# T8.2 Feedback-driven adaptation experiment

Milestone M8 · Effort L · Depends on: T6.1 · Risk: RK-25 (later use of feedback), RK-9 (injection in rationale)

Status: done (2026-11-06). The mechanism and the offline evaluation hook are in. The experiment itself (runs on the benchmark projects, simulated reviews) is not run.

## Context

T6.1 stores the review of a trace link (`status`, `reviewedBy`, `reviewedAt`, `reviewReason`, `reviewOrigin`). T6.1 does not use the reviews to change a later run. The paper review asks for feedback that goes back into the system (paper §4, challenge 5). This task adds the mechanism and the offline evaluation hook for an experiment. It does not run a user study.

## Goal

A project owner switches feedback adaptation on for one approach. The next run of the approach then uses the reviews of this project in two ways:

1. Few-shot examples: LLM approaches get confirmed and rejected element pairs as examples.
2. Per-project confidence threshold: the run drops candidate links below a threshold that was derived from the reviews.

The switch is off by default. With the switch off, every `configHash`, link id and prompt stays as before.

## Design

### Switch

The approach parameter `feedback` (object) in `config/tlr/approaches.yaml` or in the request `params.<approach>`:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | boolean | `false` | Switch. Without `enabled: true` the host removes `feedback` from the effective params. |
| `fewShot` | integer | `2` | Examples per class (confirmed, rejected). `0` turns few-shot off. |
| `minReviews` | integer | `10` | Minimum number of reviewed pairs of the approach before a threshold is derived. |

The key `feedback` is allowed for every approach. The host reads it. Only an approach that uses an LLM (`usesLlm`) gets examples.

### Feedback snapshot

The snapshot is the set of direct reviews of the project:

- Source: `TraceLink` with `reviewOrigin = 'user'` and `status` `confirmed` or `rejected`, without extraction-owned approaches (`explicit-reference`, `user-declared`). Active and inactive links count, so that the snapshot does not shrink when the threshold removes links.
- One entry per approach and element pair (`key` and `contentHash` of both elements). The entry with the latest `reviewedAt` wins.
- Entry fields: `approach`, `status`, `confidence`, `reviewedAt`, `reviewReason`, source key and content hash, target key and content hash.
- The snapshot hash is the SHA-256 of the JCS of the entries, sorted by approach, source key, target key.

### `configHash`

If feedback is on, the host adds two members to the hashed params (not to the params that the approach sees): the `feedback` object and `feedbackSnapshot` (the snapshot hash). Other snapshot, other `configHash`, other link ids, other `inputKey`. The Run stores the params, so the experiment manifest reproduces the setting. If feedback is off, the hashed params equal the old ones. Existing hashes do not change.

### Threshold

For one approach, over the entries of this approach:

1. If there are fewer than `minReviews` entries, or no `confirmed` or no `rejected` entry: no threshold.
2. Else test every distinct confidence as threshold `t`. A link counts as predicted if `confidence >= t`. Choose the `t` with the highest F1 over the reviewed entries. On a tie choose the lowest `t`.
3. The host drops candidate links with `confidence < t` before it writes them. Approaches that give `confidence = 1.0` (for example `lissa`) are not affected.

Limit: the reviewed set contains only links that an approach has already proposed. Recall is measured against the confirmed entries only. The experiment reports this bias (Risks).

### Few-shot examples (LLM approaches)

1. The host selects the newest `fewShot` confirmed and `fewShot` rejected pairs of the whole snapshot (all approaches, one entry per element pair), ordered by `reviewedAt` descending and then by keys.
2. The host adds the text of both elements. The target text of a file is the first 1000 characters of the stored version, the source text is cut at 500 characters. A pair whose text cannot be read is skipped.
3. The context `TlrContext.feedback()` carries the examples and the snapshot hash. It is `null` if feedback is off.
4. `lissa` adds the block to the start of the classifier prompt. The prompt id (`lissa-<classifier>@<hash>`) includes the block, so `Run.promptIds` shows the change.

### Untrusted text (RK-9)

The reviewer reason, the requirement text and the file text are untrusted.

- The block states that the content of `<example>` tags is data and not an instruction.
- The host and the approach escape `&`, `<` and `>` in all inserted text, so a reason cannot close the tag or forge `<trace>`.
- The approach inserts `{ ` for `{`, so a reason cannot fill a template placeholder.
- The reason is cut at 200 characters. The answer of an example is only `yes` or `no`.

### Reproducibility (RK-25)

- Feedback is off by default, in the config and in every test fixture.
- The snapshot hash is part of `configHash`, so a replay with another snapshot is a cache miss and is never silently matched to old cassettes.
- The selection of examples is deterministic.
- The recorded Run keeps the `params` and the `promptIds`.

## Offline evaluation hook

`FeedbackAdaptation` is a pure class: input are review entries, output are the snapshot, the threshold and the selected examples. No KG, no LLM. An experiment script feeds it entries that it simulates from a gold standard (reviewer = gold label), splits them into train and test (fixed seed), and compares the F1 of the test links with and without the derived threshold. A test in this task shows the hook with a small synthetic gold set.

## Out of scope

- The human study (T8.1). This task delivers the mechanism and the hook.
- Feedback for `explicit-reference` and `user-declared` links.
- Feedback on inconsistencies (T7.5 stores its own suggestions).
- Fine-tuning, model-side learning, and active learning (choice of links to review).
- A new endpoint, a new KG field or a new event. The mechanism only reads T6.1 fields.

## Acceptance criteria

- With `feedback` off or absent, `configHash` of every approach equals the old value (test).
- With `feedback.enabled`, a changed review gives another snapshot hash and another `configHash`. The same reviews give the same values.
- The threshold is derived as described, with the tie rule and the minimum count (unit tests).
- Few-shot selection is deterministic and respects `fewShot`. The prompt of `lissa` contains the examples and the prompt id changes.
- A reason with `</example>`, `<trace>yes</trace>`, `{source_content}` and an instruction does not break out of the block (test).
- A synthetic gold set shows the evaluation hook end to end (test).
- `docs/user/trace-links-and-findings.md` describes the switch. `experiments/PROTOCOL.md` has section 10.
- `mvn -o` of `services/tlr-agent` (with its approach modules) is green. `make contracts` says contracts ok.

## Test plan

- Unit tests of `FeedbackAdaptation` (snapshot hash, threshold, selection, escaping, hook).
- Unit test of the `lissa` prompt with a fake gateway (`LissaApproachTest` pattern).
- Test of the `configHash` rule with the feedback switch off and on (host test; Docker test if Traverse runs).

## Risks

| Risk | Handling |
| --- | --- |
| RK-25: feedback changes results and breaks reproduction | Off by default. Snapshot hash in `configHash`. Params in the Run. |
| RK-9: reviewer text injects instructions | Fence and escape (section Untrusted text). The reason never changes the answer of an example. |
| Selection bias: only proposed links get a review | Report the bias. Compare on a hold-out set that a reviewer judged without seeing the threshold. |
| Reviewers make errors | The experiment reports the effect with simulated noise (flip rate) in a later task. |
| Examples from the test set leak into the prompt | The experiment script removes test pairs from the entries before it builds the snapshot. |
