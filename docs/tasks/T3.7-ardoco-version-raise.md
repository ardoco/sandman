# T3.7 Raise `ardoco.version` for TLR, text and shadow to the release of T3.5

Milestone M3 · Effort M · Depends on: T3.5 (case A), T2.7, F-1b (shared code model per run, T5.4 next step for `ingest-tlr`) · Checks RK-22, T5.4

Status: open, waiting for T3.5 (2026-10-18)

## Context

After T3.5, the inconsistency agent uses the new ArDoCo release (likely `2.2.0`). The root property `ardoco.version` stays `2.1.0`. It feeds `approach-ardoco` (`ardoco`, `ardocode`, `transarc`), `code-extractor-ardoco`, `sandman-ardoco-text` and `sandman-ardoco-shadow`. Two ArDoCo versions then exist in the repository. This task removes the second version.

`sandman-ardoco-shadow` holds a copy of `CodeModelWithCompilationUnitsAndPackages` with caches (F-1). Quarkus loads it instead of the ArDoCo class (`services/tlr-agent/src/main/resources/application.properties`, lines 11 and 12). The class comment says: raise `ardoco.version` only after a comparison with the new original.

## Findings (2026-10-18, `v2.1.0` against the pin `0d1f22b`)

Verified:

1. The shadowed class changes. The DTO constructor passes `codeModelDto.codeFiles()` to `super`. A new constructor takes `List<CodeFile> codeFiles`.
2. `CodeModel` gains `codeFiles`, `getClasses()` and `getCodeFiles()`. `CodeModelDto` gains a 4th component `codeFiles`. The DTO constructor maps a `null` list to an empty list, so ACM files without `codeFiles` still load (source check, not run).
3. Changed classes that SANDMAN imports on the TLR side: `CodeModel`, `CodeModelWithCompilationUnits`, `CodeItem`, `CodeItemRepository`, `Datatype`, `ProgrammingLanguage`, `ArdocoResult`, `DataRepositoryHelper`, `ArchitectureConfiguration` (`@Nullable` metamodel only), `CodeConfiguration`, `ModelProviderAgent`, `AllLanguagesExtractor`, `LargeLanguageModel`.
4. `pipeline-tlr` gains the runners `Artemis`, `ArtemisInExArch` and `ArtemisInTransArC`.
5. `core/tests-base` benchmark resources change (gold standards and `codeModel.acm` of several projects). Upstream benchmark numbers can change.
6. T3.3 open point 4: the MediaStore deviation (2 extra `download` text findings) comes from the release TLR (18 links) against the ID-branch TLR (29 links).

Unknown:

* U1: Whether the release adds changes after the pin to these classes (repeat the diff against the release).
* U2: Whether `code-extractor-ardoco` must write `codeFiles` to keep `CodeModelEquivalenceTest` equal.
* U3: Whether the release TLR gives 29 links on MediaStore, so the T3.3 deviation goes away.
* U4: Whether the CoreNLP version of the new `pipeline-tlr` differs from `corenlp.version`.
* U5: Whether F-1b adds more logic to the shadow class (re-check after F-1b lands).

## Goal

All SANDMAN modules use one ArDoCo version. The shadow class matches the new original plus the F-1 and F-1b caches. Equivalence tests, goldens and performance numbers are re-baselined with recorded causes.

## Steps

Each step ends with its check. Keep the handoff note `.work/T3.7.md` up to date.

1. Diff the TLR-side API. Use the import list of T3.5 step 2 against `v2.1.0`.
   ```sh
   git -C "$W" diff --name-status v2.1.0 "v$V" -- '*.java' | grep -F -f "$TMPDIR/ardoco-imports.txt"
   git -C "$W" diff v2.1.0 "v$V" -- core/framework/common/src/main/java/edu/kit/kastel/mcse/ardoco/core/api/models/CodeModelWithCompilationUnitsAndPackages.java
   ```
   Check: each listed class is recorded in `.work/T3.7.md` with "signature change: yes or no".
2. Re-sync the shadow class (decision 3). Update the class comment and the `ponytail:` comment to the new version.
   Check: `CodeModelWithCompilationUnitsAndPackagesCacheTest` passes. `diff` of the shadow against the new original shows only the cache lines.
3. Raise `ardoco.version` in the root `pom.xml`. Delete `ardoco.id.version` (decision 1). Compare `corenlp.version` with the version that `pipeline-tlr` declares (U4).
   Check: `mvn -q dependency:tree -Dincludes='io.github.ardoco*,edu.stanford.nlp'` lists one ArDoCo version and one CoreNLP version.
4. Update the approach versions (decision 2).
   Check: `VersionTest` passes.
5. Check the Quarkus class loading. The `removed-resources` key names `io.github.ardoco.core:common`. If the artifact or the class path changes, update lines 11 and 12 of `application.properties`.
   Check: `mvn -pl services/tlr-agent -am verify` passes. Start the `tlr-agent` image and run one `ardocode` job. The log shows the shadow cache hits (F-1 check).
6. Run the TLR equivalence tests: `BenchmarkEquivalenceTest`, `TransarcEquivalenceTest` and `ExarchPortTest` of `approach-ardoco`, and `CodeModelEquivalenceTest` of `code-extractor-ardoco` (decision 4, U2).
   Check: pass, or new expected values with a recorded upstream cause.
7. Re-record the T3.3 link files in `detector-ardoco/src/test/resources/tlr-ardoco-links` from `approach-ardoco`. If MediaStore now equals the standalone runner, delete the `extra` entry (U3).
   Check: `TlrLinksEquivalenceTest` and `TlrLinksEquivalenceKgTest` pass. Update T3.3 Results and close its open point 4.
8. Re-baseline the goldens.
   ```sh
   make e2e && make replay-twice
   ```
   Check: pass. If the `toolVersion` or links change, regenerate with `make record-cassettes` and record the cause in the commit message.
9. Re-run the performance budget: `make perf`. Add a column "After T3.7" to the F-1 table in `docs/tasks/T5.4-performance-budget.md`.
   Check: no item is more than 10 % slower than "After F-1b". If one is slower, record the cause.
10. Update the docs: ADR-0015 amendment (R-022 line: TLR uses the new release), `services/tlr-agent/THIRD-PARTY.md`, the comment in `libs/java/ardoco-text/pom.xml`, the plan row T3.7.
    Check: `grep -rn '2\.1\.0' services libs --include='*.md' --include=pom.xml` lists only NAER or history statements.

## Acceptance criteria

1. One ArDoCo version in all modules. `ardoco.id.version` is gone.
2. The shadow class equals the new original plus the cache changes. Its test passes.
3. All equivalence tests pass. Changed values have a recorded cause.
4. The T3.3 MediaStore deviation is closed, or its new cause is recorded.
5. `make e2e`, `make replay-twice` and `mvn -B verify` pass.
6. T5.4 has an "After T3.7" column.

## Rollback

1. Revert the commits of this task (`git revert <sha>`). The shadow, the version property, the approach versions and the goldens must revert together.
2. T3.5 stays done. The repository returns to two ArDoCo versions, which is a valid state.

## Risks

* The shadow class misses an upstream change. ArDoCo then reads stale data. Mitigation: decision 3, step 2 diff check.
* Upstream benchmark numbers change. Equivalence values move. Mitigation: compare with the standalone runner of the same release, not with old numbers.
* The CoreNLP version changes. The `corenlp-gateway` and the agents then annotate differently. Mitigation: step 3 check. If it differs, align the gateway image in the same task.
* Approach version change triggers a full TLR re-run on existing projects. Mitigation: expected one-time cost. Mention it in the release notes.
