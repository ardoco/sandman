# T7.5 Resolution suggestions and clarification questions

Milestone M7 · Effort M · Depends on: T3.4, T6.2 · Risk: RK-9 (injection into LLM prompts)

Status: done (2026-11-06). Deviations: the console shows only the newest recorded result; the check order is authorize, then flag (a disabled flag must not reveal itself to users without access).

## Context

A triager sees an open inconsistency and its evidence (T3.4). The triager must decide a cause (T6.2) and a fix alone. An LLM can propose likely resolutions and questions that help the decision. Such text is advice only. It must not change any artifact or any inconsistency.

## Goal

A triager can ask for suggested resolutions and clarification questions for one open inconsistency of severity warning or error. Each item cites evidence ids of that inconsistency. The system records every result with its provenance.

## Design

The feature lives in the query-service. The service already holds the LLM access (`NlService.llm`), the project `llmPolicy` and the evidence read path.

| Item | Decision |
| --- | --- |
| Flag | `suggestions.enabled` in `config/query/strategies.yaml`. Default `false`. A disabled flag answers 501. |
| Route | `POST /v1/inconsistencies/{id}/suggestions` (new, role `triager`) creates and records one result. `GET` on the same path lists the recorded results, newest first (role `viewer`). |
| Gate | Status must be `OPEN` or `REOPENED` (else 409). Severity must be `warning` or `error` (else 422). |
| Input | Title, description, type, severity and the involved elements (id, key, label, name, path, excerpt) and trace links (id, approach, confidence, keys). All text is untrusted. |
| Prompt | One system prompt and one user message. The data sits between `<finding>` and `</finding>` as JSON. The characters `<` and `>` are escaped. The prompt says to ignore instructions in the data. |
| Output | JSON with `suggestions` and `questions`, each an array of at most 5 items `{text, evidenceIds}`. The service passes the schema as `response_schema` and validates the answer again. |
| Grounding | An id is allowed if it is an id of an involved element or trace link of the input. The service drops other ids. The service drops an item that has no id left. An empty result carries a warning. |
| Recording | One row per result in the SQLite store of the query-service: id, inconsistency id, project, time, actor, route, resolved model, SHA-256 of prompt and schema (`promptHash`), the items. |
| Write rule | The feature writes no KG node, no artifact and no status. It calls no transition. The recorded row lives in the user store only. |
| Failure | A model or parse failure gives 502 with a problem body. No row is recorded. |

## Scope

In:
1. Module `suggest.py`: prompt, schema, grounding, prompt hash.
2. Migration `002_suggestions.sql` and store methods.
3. The two routes, the OpenAPI entries and the config schema entry.
4. Console: a button and the latest recorded result on the inconsistency page.
5. Unit tests with a scripted LLM client. User docs.

Out:
- Applying a suggestion. No automatic edit, no status change, no pull request.
- Streaming, multi-turn chat, suggestions for severity `info`.
- Storing results in the KG. The store row is enough for audit.
- Retention of old rows. Rows are small. Add pruning when they grow.

## Acceptance criteria

1. With the flag off, `POST` answers 501 and no LLM call happens.
2. A severity `info` finding answers 422. A finding with a status other than `OPEN` or `REOPENED` answers 409.
3. A valid answer is returned and recorded with model, `promptHash` and actor.
4. An id outside the input is dropped. An item without an id is dropped.
5. An answer that violates the output schema answers 502 and records nothing.
6. Text that tries to close the data fence stays inside it. The console shows suggestion text escaped.
7. The viewer role cannot `POST`. The role check uses the project of the inconsistency.
8. The KG reader and the owner client see no write call.
9. `make contracts`, `ruff` and `uv run pytest services/query-service` are green.

## Test plan

- Scripted LLM client (`ScriptedLlmClient`): no live LLM.
- Tests: flag off, severity gate, status gate, grounding, schema violation, injection text, recording and listing, role check, console button.

## Risks

- RK-9: finding text comes from user artifacts. Mitigation: fence, escape, schema, grounding, no tool calls, no write path.
- A suggestion can be wrong. The console labels it "AI suggestion, not verified".
- Cost: the call is explicit, per finding, off by default, and subject to the existing LLM budget.
