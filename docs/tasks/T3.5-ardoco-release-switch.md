# T3.5 Switch `ardoco-id` and `artemis-id` from the pinned build to a published ArDoCo

Milestone M3 · Effort S · Depends on: upstream merge of `feature/make-inconsistency-great-again` (Q-15), T3.1, T3.2, T3.3, T2.7 committed · Checks Q-15, RK-22

Status: open, waiting for the upstream merge (checked 2026-10-18)

## Context

`detector-ardoco` (T3.1, T3.2) uses the ArDoCo inconsistency branch. Maven Central has no Artemis classes. `scripts/ardoco-id-bootstrap.sh` builds the pinned commit `0d1f22b` from source and installs it as `2.1.0-SNAPSHOT` (ADR-0015 B1). The TLR approaches (`ardoco`, `ardocode`, `transarc`), `ardoco-text`, `ardoco-shadow` and `code-extractor-ardoco` use the release `2.1.0` (`ardoco.version` in the root `pom.xml`).

The branch will merge into ArDoCo `main` soon. This task defines the trigger, the decision tree and the switch of the inconsistency agent. T3.7 raises `ardoco.version` for the TLR side later.

## Findings (2026-10-18)

Verified (network and local clone `${TMPDIR}/ardoco-id/ardoco`):

1. Upstream refs: branch head `90fd133` (2026-10-09), `main` head `ffd610f` (2026-10-16), tags `v2.0.1`, `v2.1.0`. The pin `0d1f22b` is not an ancestor of `main`.
2. Pin to branch head: no Java change. The branch merged `main` (release 2.1.0). The version is now `2.2.0-SNAPSHOT`. NAER is `2.1.0` in both poms. The `sed` patch of the bootstrap is not needed at the branch head. This closes the TODO item "switch the branch to NAER 2.1.0".
3. Maven Central: `io.github.ardoco.id:pipeline-id` release `2.1.0`. `io/github/ardoco/tlr/artemis` and `io/github/ardoco/id/artemis-inconsistency-detection` return 404.
4. Central snapshots (`https://central.sonatype.com/repository/maven-snapshots/`): `pipeline-id` `2.2.0-SNAPSHOT` (2026-10-08) from `main`, without Artemis. `main` commits of 2026-10-16 are not in it, so snapshots are not published on every push.
5. `v2.1.0` to `0d1f22b`: 121 Java files change (+4819/-1005). 26 of them are classes that SANDMAN imports (command in step 2). The ID side adds Artemis classes. The TLR side changes `CodeModel*`, `CodeItem`, `CodeItemRepository`, `ArdocoResult`, `DataRepositoryHelper`, `ArchitectureConfiguration`, `CodeConfiguration`, `ModelProviderAgent`, `AllLanguagesExtractor` and `LargeLanguageModel`. These TLR changes are T3.7 scope.
6. `.work/T3.5.md`: with `ardoco.id.version=2.1.0`, `ardoco-id` compiles and the T3.3 counts match. Only the Artemis runner fails.

Unknown:

* U1: Merge date, merge style (merge commit or squash) and the next release number (likely `2.2.0`).
* U2: Whether the release publishes `tlr:artemis` and `id:artemis-inconsistency-detection`.
* U3: Whether the merge changes Java code after `90fd133`.
* U4: How upstream publishes snapshots (`verify.yml` has `deploy: false`).
* U5: Whether the `langchain4j-bom` bump on `main` conflicts with the Quarkus BOM (RK-22).
* U6: Whether the F-1 reuse key contains the detector version (if yes, one full re-detection after the switch).

## Goal

The inconsistency agent gets ArDoCo from Maven coordinates. No build from source remains in CI, the Dockerfile or the Makefile. If no release exists yet, the pin moves to the merge commit on `main`, and the NAER patch goes away.

## Trigger: detect the merge

Run these commands from the repository root. Run them on request, or once a week while the task is open.

```sh
# 1. Upstream refs. If the branch line is missing, the branch is deleted (usually after the merge).
git ls-remote https://github.com/ArDoCo/ardoco.git refs/heads/main refs/heads/feature/make-inconsistency-great-again 'refs/tags/v*'

# 2. Artemis on main. Works for merge commits and squash merges.
W=${ARDOCO_WORK:-${TMPDIR:-/tmp}/ardoco-id}/ardoco   # clone made by make ardoco
git -C "$W" fetch -q --tags origin main
git -C "$W" ls-tree -d --name-only origin/main tlr/stages-tlr/artemis inconsistency-detection/stages-id/artemis-inconsistency-detection
git -C "$W" merge-base --is-ancestor 0d1f22b origin/main && echo "pin is on main (merge commit)"

# 3. Release on Maven Central with Artemis.
C=https://repo1.maven.org/maven2/io/github/ardoco
curl -fsS -m 20 "$C/id/pipeline-id/maven-metadata.xml" | grep -o '<release>[^<]*'
for a in tlr/artemis id/artemis-inconsistency-detection; do
  curl -s -o /dev/null -m 20 -w "$a %{http_code}\n" "$C/$a/maven-metadata.xml"
done

# 4. The release jar holds the Artemis runner (set V to the release from step 3).
V=2.2.0; J=$(mktemp -d)/pipeline-id.jar
curl -fsS -m 60 -o "$J" "$C/id/pipeline-id/$V/pipeline-id-$V.jar" \
  && unzip -l "$J" | grep 'id/execution/runner/ArtemisInconsistencyDetection.class'
```

## Decision tree

| Case | Condition (trigger steps) | Action |
|------|---------------------------|--------|
| A | Step 3 shows a release newer than `2.1.0`. Both Artemis artifacts return 200. Step 4 finds the runner. | Do the full switch (steps 1 to 9). T3.5 is done. Then T3.7 can start. |
| B | Step 2 lists both Artemis directories, but case A is false. | Do the interim re-pin (step B). T3.5 stays open. Check the trigger again after the next release. |
| C | Step 2 lists no Artemis directory. | Do nothing. The pin `0d1f22b` stays. |
| D | A release exists, but without Artemis (step 3 shows 404). | Treat as case B. `ardoco-id` alone can not switch: `artemis-id` needs the same `common` on the same classpath. |

Do not depend on remote snapshots in any case (finding 4, decision 2).

| # | Question | Decision [default] |

## Acceptance criteria

1. Case A: `detector-ardoco` uses Maven Central coordinates. No file in CI, the Makefile or the Dockerfile builds ArDoCo from source.
2. The enforcer bans snapshot ArDoCo artifacts in `detector-ardoco` and `inconsistency-agent`.
3. All tests of step 6 pass. Changed counts have a recorded cause.
4. The detector versions name the release. No code or golden file contains `0d1f22b`.
5. ADR-0015, `THIRD-PARTY.md`, the plan and the listed docs describe the new state.
6. Case B: the bootstrap builds the merge commit without a patch. T3.5 stays open.

## Rollback

1. Revert the commits of this task in reverse order (`git revert <sha>`). Do not use `reset --hard` on `develop`.
2. The script, the pin `0d1f22b` and the CI cache key come back with the revert. The first CI run rebuilds the cache (key `ardoco-id-0d1f22b…`).
3. If only the TLR-side check (step 4) fails, keep the bootstrap and record the blocker in `.work/T3.5.md` and the plan row.
4. Revert the detector version and the goldens together with the dependency change. They must stay in one state.

## Risks

* The release changes ID behaviour. The T3.3 counts change. Mitigation: record the cause, compare with the standalone runner of the same release.
* The `langchain4j-bom` bump conflicts with the Quarkus BOM (U5, RK-22). Mitigation: `TlrLinksEquivalenceKgTest` runs on the Quarkus classpath. If it fails, pin `langchain4j` in `detector-ardoco`.
* Two ArDoCo versions live in two images until T3.7. Mitigation: separate JVMs. No module of `tlr-agent` depends on `detector-ardoco`.
* A changed detector version invalidates reuse (U6). Mitigation: expected one-time cost. Record it.
